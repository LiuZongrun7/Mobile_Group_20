# 用量数据从哪来

这份文件回答一个问题：**用户在我们的软件里填点什么，我们就能替他把自己的用量拉回来。**
它是 `data/remote/` 那层 fetcher 的规格，和 [`CONTRACTS.md`](CONTRACTS.md) §4 的数据流配套。

**先把两条路分开**，它们经常被混着说：

| | 谁去取 | 用户做什么 | 在哪 |
| --- | --- | --- | --- |
| **拉取 fetch** | 我们，主动打 provider 的接口 | 在 App 里填一次凭据 | `data/remote/` ← **主线** |
| **导入 import** | 不用取，用户给文件 | 手动导出、把文件拖进来 | `data/importer/` ← 兜底 |

**两条路产出的东西是同一个**（`UsageCall`），所以下游——去重、日汇总、结算、资源余额（游戏 2026-09-30 移出，这套换算本身照旧）——
完全一样。这也是为什么 fetcher 层很薄：它只负责**把字节弄到手**，解析仍然归 `data/importer/`。
（DeepSeek 那条最明显：控制台点「导出」和程序去拉，拿回来的是**同一个 zip**，
我们只是替用户点了那个按钮。）

## 2. 粒度问题：这条不定下来，去重那条验收会打架

`UsageCall` 现在的注释是「**一次**模型调用的原始记录」，`id` 要能由「提供方 + 请求 id + 日期」
算出来。但 **OpenAI 给的是时间桶，没有请求 id**。两条路：

- **A（推荐）**：桶也落成 `UsageCall`，`id` 用 `provider + 桶起点 + 模型 + 项目`。
  **列不用改，表结构不动**——桶行和调用行的列完全一样。代价是「一行 = 一个桶」
  而不是一次调用，**桶来源的行做不了按会话分析**（桶里没有会话信息）。
  因为 `bucket_width` 最大 `1d`、最小 `1m`，**桶不会跨天**，日汇总照样滚得出来。
- **B**：桶只落到 `DailyUsage`，不下钻到 `UsageCall`。那 OpenAI 这条就永远看不到单次调用，
  和「`UsageCall` 是唯一事实来源」的说法直接冲突。

**已定：走 A**（2026-09-26）。表结构不动，桶行和调用行同列；桶不跨天，日汇总照样滚得出来。

代价认下来——桶行没有会话信息。为了让它**可判断**（而不是靠人记），
`id` 加一个前缀来区分粒度：

```
call:<provider>:<请求 id>:<yyyy-MM-dd>
bucket:<provider>:<桶起点毫秒>:<model>:<projectId>
```

**前缀是必需的，不是装饰**：`UsageCall` 里没有别的字段能告诉你这行是桶还是调用，
而「哪些行能做按会话分析」必须能算出来。有 `bucket:` 前缀的行，
Sessions 那类图表要过滤掉，否则会以为数据丢了。

顺带一笔：`Source.IMPORTED` 这个名字现在也覆盖拉取来的数据。**不改枚举**
（改它要动 `contract`、服务端字段、桩数据三处），报告里说明一句就行。

>
> 反转那一次是"新增 API 中转"：用户的真上游 key 存到服务器上，转发时注入。
> **2026-09-30 中转整块删除**（见 [`SERVER_API.md`](SERVER_API.md)），
> **那个反转随之撤销**——服务端不再替任何人转发，也就没有用户的 provider 凭据
> 要放在我们这儿，`relay_secrets` 那张表都删了。所以下面"绝不上传服务端"这条
> **重新成立**，而且这次是完整的：连转发那条例外也没有了。
>
> 下面 §5 整节保留原样（那是"当时为什么改、后来又为什么不改"的记录），
> **但读的时候要知道它的结论已经作废**：它描述的转发路径、SSRF 白名单、
> 上游密钥落库，全部不存在了。§5 开头我加了一段现状说明。

| key | 谁的 | 存哪 |
| --- | --- | --- |
| 服务端调模型用的 key（智能体 / 将来的"后端调模型"） | 我们自己的 | **只在服务端**，客户端永远看不到（不变） |

| ~~转发用的上游 key~~ | ~~用户的~~ | ~~**服务端**~~ ← **2026-09-30 中转删除，这一类没有了** |
| ~~relay key（中转凭据）~~ | ~~我们的~~ | ~~客户端，明文~~ ← **2026-09-30 起不再签发也不再认** |

> **2026-02：身份从 relay key 换成了账号。** 这一节原来把「用户查自己用量用的凭据」
> 和 relay key 当成同一件东西（因为那时 relay key 就是身份）。现在不是了：
> 账号会话 token 是**唯一**身份（登录论坛、读用量、结算都用它）。
> ~~relay key 只是「怎么把用量交上来」的一条通道~~ **（2026-09-30 改）
> 那条通道也没了**——中转删除之后 `tt_` 前缀的凭据不再存在，
> 所以"两种凭据两种存法"的对比现在只剩前半句：账号 token 用 Keystore 加密，
> 因为它是**密码换来的**、用户为它敲过一个密码（换设备要重登一次，代价可接受）。

**原决定（2026-09-26，关于「查用量」那一类，仍然成立）：**

- **凭据只落设备本机，明文存 `SharedPreferences`，不加密。** 这是**有意的取舍**，

- ~~**但绝不上传服务端。**~~ ← 这一条 **2026-09-27 被 §5 反转，2026-09-30 又转回来了**

- ~~**relay key 也走明文（2026-09-27）**。它一开始用 Android Keystore 加密存，

## 4. 实测记录

### 已验：DeepSeek 用量导出（2026-09-26，真实账号导的一份 7 天数据）

导出的是一份 `usage_data_2026-09-20_2026-09-26.zip`，解开是
`amount-*.csv` + `cost-*.csv` 两个文件。看下来的结论，**有三条和原来的假设不一样**：

1. **列名和值域**（原来第 3 条待验项）：
   - `amount-*.csv`：`user_id, utc_date, model, api_key_name, type, price, amount`
   - `type` 只有四个值，正好对上我们的四桶：

     | 导出里的 `type` | 我们的桶 |
     | --- | --- |
     | `input_cache_miss_tokens` | `input` |
     | `input_cache_hit_tokens` | `cacheRead` |
     | `output_tokens` | `output` |
     | `request_count` | `calls`（不是 token） |

     **没有 cacheWrite**，和上面 §1 的预判一致。
   - 行的粒度是 `(天, 模型, api_key_name, type)`，一周 74 行，唯一。
   - `request_count` 那几行 `price` 是**空字符串**，不是 0。
   - 两个 CSV 都带 **BOM**，按第一列名匹配会失败。

2. **金额是人民币，而且自带单价** —— 这条推翻了两处假设：
   - `cost-*.csv` 给的日金额是 **CNY**，不是美元。项目内部计价用微美元，所以导入时
     要做一次反向换算，见 `CONTRACTS.md` §9。
   - `amount-*.csv` 每行自带 `price`。用「`amount × price` 按天求和」和 `cost-*.csv`
     的日金额对账，**7 天全部精确吻合**。所以**根本不需要自己维护价目表**——
     峰谷价、折扣都已经在 `price` 里了。这也是 `UsageCall.costMicros` 存在的理由。

3. **峰谷价是真的，而且正好 2 倍**（cacheRead 0.02 / 0.04，input 1 / 2，
   output 4 / 8，单位是「元 / 1M tokens」）。同一天里两档会**同时出现**，而导出里
   **没有任何小时信息**，所以还原不出哪笔是哪个价——但也不需要还原，因为每行自带
   `price`。这条同时解释了 `CONTRACTS.md` §9 里「低谷价」那条为什么可以先不管。

4. **天是按 `+08:00` 切的**，和我们一致，不是 UTC。`CONTRACTS.md` §3 原来写错了，
   已经改掉。

5. **⚠️ 这份数据不能进仓库。** 里面有 `user_id`（UUID）、**打过码但仍可辨的
   `api_key`**、以及 `api_key_name` 里**真实同学的姓名**。要用它当测试样例，
   必须先把这三列换掉（`uid-1` / `key-a` / `同学A`），再进
   `app/src/test/resources/`。原始 zip 只留在本机。

### 还没验

1. **OpenAI 的 `input_cached_tokens` 到底有没有值**——要真 key 打一次。它要是恒为 0，
   `cacheRead` 这一桶就只能靠解析本地日志补。**这条到现在没动过**，
   `DATA_SOURCES.md` §1 那个「恒返回 0」是社区报告，不是我们测的，别当结论用。
2. **三家接口在这台机器 / 大陆网络下通不通**——要不要代理。通不了的话演示就得换网络。
3. **OpenAI 那套四桶口径能不能真的填满**——上面第 1 条是它的前置。

## 5. 2026-09-27：为什么还是把上游 key 放到了服务器上

> ## 🚫 这一整节已经作废（2026-09-30），保留作历史记录
>
> **结论先给：中转整块删除了，用户的 provider 凭据从来没有、现在也不需要上传服务端。**
> 新建的服务端接口见 [`SERVER_API.md`](SERVER_API.md)：账号、用量、预算、价目、赛季、
> 智能体；没有转发、没有 `/keys*`、没有 SSRF 白名单、没有上游密钥表。
>
> 新方向（ModelPilot 大纲）是「**用户在 App 里提问 → 后端用我们自己的模型连接调用 →
> 产生用量 → 记账**」——用量由**我们自己的调用**产生，而不是从用户的流量里旁路抽取。
> **那条路还没写**，但它一旦写出来，"用户把 key 交给我们"这个前提就不存在了。
>
> **下面原文一个字不改地留着**，因为"当时为什么否掉（§3）→ 后来为什么还是做了（§5）
> → 最后为什么又删了（这里）"三段连起来才讲得清这个取舍。只留结论的话，
> 下一个人会以为这是随手改的。
>
> 读原文时注意两件事：① 里面写的**风险判断本身仍然有效**（"服务端只要有一个口子
> 就是一起漏"——那句话现在重新适用）；② 里面提到的 `SERVER_API.md` 现在叫
> `SERVER_API.md`，提到的 `FORUM_RELAY_ALLOWED_HOSTS` / `_ALLOW_PRIVATE` /
> `_SELF_HOSTS` / `_REQUESTS_PER_MINUTE` 四个 env 变量**已经不起作用了**。

**决定：新增 API 中转。** 用户在 App 里填自己的 `上游 URL + 上游 API key`，
服务端发一个 relay key；把 cc-switch 的供应商 base URL 指向我们的中转，
请求原样转发到上游，响应里的 usage 顺手落库。接口契约见 `SERVER_API.md`
（**2026-09-30 改**：该文件已改名 [`SERVER_API.md`](SERVER_API.md)，中转那部分删除）。

### 它换来了什么（这是当时否掉时没算到的）

`data/remote/package-info.java` 和 `OPEN_SOURCE.md` §2 都把 LiteLLM 写成
**对照物**：它是代理网关，**我们不代理流量**。中转把这个差异化取消了——
换来的东西是实打实的：

| | 拉取 / 导入（原方案） | 中转 |
|---|---|---|
| 数据粒度 | 时间桶（OpenAI）或 (天,模型,类型)（DeepSeek） | **逐次调用** |
| 解析账单文件 | 要（BOM、列名、人民币换算、峰谷价） | **不要** |
| `cacheWrite` 桶 | **两家都拿不到** | **响应里就有** |
| 会话信息 | 桶行没有，做不了按会话分析 | 有 request id |
| 价目表 | 要自己维护 | 不要（响应自带 token 数） |

**`cacheWrite` 那一格原本是填不满的**（§1 的两张表都写着拿不到），而大纲
要求四个桶都能计。代理路径第一次让这个桶有了真实来源。

### 代价（必须一起讲）

1. **我们替用户保管真上游 key。** §3 当时那句「服务端只要有一个口子就是一起漏」
   **仍然是对的风险判断**，只是当时选择承担它。缓解措施写在 `SERVER_API.md`：
   relay key 明文不落库（只存 sha256）、上游密钥单独一张表（查身份那条路径不碰它）、
   管理接口任何响应都不回上游密钥。
   **（2026-09-30 改）这一条最后没有被承担**：中转删除，`relay_secrets` 表
   （上游密钥）和 `relay_keys`（凭据）一起 `DROP` 了，"放全班 API key 在一台机器上"
   这件事从来没有真正发生。**但 §3 那句话本身仍然要留着**——下一个想往服务端
   放第三方密钥的人应该先读它。
2. **离线能力**：服务器不可用时转发不通。原来「本机存反而更快、离线也能用」这条
   优势在中转路径上没有了（导入路径还在，没删）。
   **（2026-09-30 改）不适用了**：现在服务端只做记账和智能体问答，App 的导入路径
   照旧离线可用。
3. **我们是唯一的失败点**：所有请求经过我们，服务挂了用户就写不了代码。
   **（2026-09-30 改）不适用了**：编码 agent 不再经过我们。**但同一个形状的风险
   换了个地方还在**——新的主链路上，用户每次提问都要经过我们调模型，
   服务挂了就用不了助手。这条要在报告里按新链路讲，别照抄旧结论。
4. **单 IP 多用户流量**：境外 provider 对「一个出口 IP 承载多个账号的官方 API 流量」
   有风控。cc-switch 官方文档自己就警告过本地路由 + 官方账号有账号风险，
   而远程多用户是那个模式的加强版。**这条要在报告里主动写明，不要等被问。**
5. **不再需要 `data/importer/` 来支撑主链路**，但那个包保留（导入仍是兜底路径）。
   **（2026-09-30 改）这句话反过来了**：新链路（用户提问 → 后端调模型）**还没写**，
   所以眼下 `data/importer/` 和它那条路仍然是唯一的取数方式，不是兜底。
