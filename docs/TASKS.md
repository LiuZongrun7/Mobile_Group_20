# 待办与验收标准

三个人各做一块。这份文档回答三个问题：**我该做什么、怎么算做完、卡住了找谁。**

> 给用 AI 读代码的人：契约字段的含义以 `app/src/main/java/com/mobilegroup20/tokentrail/contract/`
> 下的类注释为准，本文只讲「要做什么」。每个包还有一份 `package-info.java` 写该放什么。
> 接口的完整方法列表见 `docs/CONTRACTS.md`，或直接看 `data/repository/` 下的五个接口。

## 0. 所有人先看这四条

1. **只用接口，不用实现。** 拿对象走 `RepositoryProvider.usage()` 这样的调用，
   不要在界面里 `new` 别人的实现类。原因见 [`README.md` §2](README.md#2-依赖方向只有一个)。
2. **改 `contract/` 里的字段要先在群里说。** 那是三个人共用的，悄悄改会让别人的代码
   编译不过。改代码和改 `CONTRACTS.md` 放同一个提交里。
3. **每个新类上面写清楚：归谁、干什么、有什么坑。** 注释是写给队友（和他的 AI）看的，
   不是写给自己回忆的。
4. **金额一律用微美元（`long`）算，`double` 一次都不要出现。** 换成人民币只在最后
   显示的那一步做，而且只在数据侧做（见 `CONTRACTS.md` §9）。

## 1. 张莉 —— 数据侧

大纲里的分工：认证、用量日志导入、Room/服务端存储、版本化定价、预算、面板。
**这一块是整条链路的地基**，另外两个人的界面全部依赖它给出的数字。

### 1.1 要实现的接口

`data/repository/UsageRepository.java`（7 个方法）和
`data/repository/BudgetRepository.java`（3 个方法）。签名照抄，别改。

| 方法 | 干什么 | 关键点 |
| --- | --- | --- |
| `importCalls(uid, calls)` | 导入一批原始记录 | **按 `UsageCall.id` 去重**，靠 Room 唯一索引 + `OnConflictStrategy.IGNORE`，返回 -1 即重复。`ImportResult` 三个计数要如实填：新增 / 重复 / 拒绝 |
| `dailyUsageFor(uid, day)` | 某天的汇总 | 只返回 `Source.IMPORTED` 的记录 |
| `dailyUsageIn(uid, from, to)` | 区间的汇总 | 区间**两端都含** |
| `monthTokens(uid, month)` | 某月四类 token 合计 | 游戏侧结算读它 |
| `summary(uid, from, to, groupBy)` | 面板用的汇总 | `Coverage` 必须填对：有数据的天数和缺失的天数 |
| `compare(uid, from, to, metric)` | 三家对比 | 只比算得出来的量（token、费用、单位成本），**不比「哪个模型更聪明」** |
| `rateFor(provider, model, day)` | 查某天的费率 | 按 `effectiveFrom` 取「不晚于该天的最近一版」，见 `PricingRate` |
| `budgetOf` / `saveBudget` / `status` | 预算上限 | 只存上限，**花销从来现算**，不存「已花」 |

### 1.2 放哪

`data/local/`（Room 三张表，见 `CONTRACTS.md` §5）、`data/remote/`（自建服务端的读写）、
`data/importer/`（日志解析）。实现类写完后在 `RepositoryProvider` 里接上。

### 1.3 汇率

微美元 → 人民币的汇率、四舍五入由**你这边**定，写在数据侧；界面只显示结果，
不自己做乘法（`CONTRACTS.md` §9）。计价本身全程用微美元，汇率只影响显示。

### 1.4 验收标准

- [ ] 同一个日志文件导入两次，`inserted` 第二次是 0，`skippedDuplicates` 等于第一次的条数，
      总额不变。
- [ ] 一笔 3 美元/百万 token 的记录，300 万 token 算出来正好是 9 美元，
      不出现 8.999999。
- [ ] 改一版费率后重算，历史那几天的金额**不变**，`DailyUsage.rateVersion` 跟着变。
- [ ] 查询只返回本人的记录：登 A 账号看不到 B 的任何数字。
- [ ] `Coverage.daysMissing` 在缺数据的日子里真的会涨（不是永远 0）。
- [ ] 空区间、反向区间、只有一天，三种情况都不崩。

`ContractMathTest` 里已经有 12 个测试盯着这些口径，实现时对照着看。
**卡住了找谁**：费率区间和 `Coverage` 的口径找刘宗润（他写的 `contract/tool/`）。

## 2. 汪庭栋 —— 论坛

大纲里的分工：论坛的帖子数据与排序。

### 2.1 当前实现与新接口

论坛采用 **News / Community 两标签 + ＋发帖**。所有登录用户共享公共帖子池；“我的帖子”只是作者筛选，不是私密内容。支持最多 9 张图片、点赞、文字评论、分页与失败重试。

新版 UI 通过 `ForumFeedRepository` → `HttpForumRepository`；现有 `ForumRepository` 的 agent 接口保留。完整契约及账号接入步骤见 [`FORUM_API.md`](FORUM_API.md)。媒体新闻是独立 `NewsArticle`，不能混成官方帖子。

### 2.2 排序与数据

- 社区页面按发布时间与 ID 倒序；评论按时间与 ID 正序。
- agent 热帖排序继续由服务端计算 rankScore；现在已有点赞交互，可以纳入真实点赞数据，但不得由客户端自行重排。
- 用量、预算仍按 uid 私有；论坛帖子与评论跨账号公共可读。
- RSS 采集工具在 `tools/news/`，每小时由团队后端调度、导入新闻表。新闻英文为主，仅 App 内更新。

### 2.3 接入状态与验收

开发期已提供“免账号测试”：调试 APK 进入独立测试区，自动获得临时身份，可以独立于账号负责人测试真实新闻、图文、点赞和评论。测试数据不进入正式帖子池，Release 构建隐藏该入口。

Android UI、HTTP 适配、账号登录和 RSS 工具已实现；论坛后端已部署到现有服务器，复用 aibox_backend 的登录账号，公网 HTTPS 双账号联调通过。部署和维护见 [`backend/README.md`](../backend/README.md)。没有 API 配置时显示准备中，不用模拟数据冒充公共池。

## 3. 刘宗润 —— 游戏与 agent

大纲里的分工：塔防游戏、服务端建议服务、五个只读工具、建议效果评估。

### 3.1 塔防引擎（`game/engine/`）

**这个包不许 import 任何 `android.*`。** 玩法逻辑（网格、放塔、敌人路径、波次、
伤害结算）写成纯 Java，这样能脱离模拟器跑单元测试，也方便调平衡。

- **几何和相机已经写好了**：`BoardGeometry`（格子 ↔ 布局坐标换算、占地判定）、
  `Cell`（格子坐标，可直接当 Map 的 key）、`Viewport`（缩放 1–2 倍 + 拖动，
  焦点缩放，拖不出空白，开局贴最右边缘），共 48 个测试（BoardGeometry 25 + Viewport 23）；
  摆建筑、占位、地形分区、核心挪动、敌人推进在 `Battlefield`（65 个测试）；
  寻路那张表在 `PathField`（12 个测试），子弹在 `Projectile`（5 个）；
  数值和价格的配平在 `Cost`/`BuildingStats`（21 个）和 `ShopCatalog`（12 个）
  ——**"弩车的 DPS 必须压在箭塔下面""弩车比箭塔贵"这类话都写成了断言**，
  它们不是注释，改数就会炸。
  整个 `game/engine/` 现在是 **164** 个测试（含 1 个跳过的 `DemoSceneProbeTest`）；
  **全项目 272 个**（另有 `contract` 12、`util` 13、`data.local` 17、`data` 19、
  `data.remote` 33、`ui.forum` 7、`ui.auth` 6、根包 1）——这两个数别混，
  272 是整个工程的总数，不是这个包的。
  （2026-09-27 从 223 重数过：多出来的是自建服务端那几个 HTTP 仓储和登录态
  的测试，**游戏侧一个没加**，164 没动。）
  玩法逻辑<b>只用 `Cell`，不要碰屏幕像素</b>；触摸事件走
  `视口换算回布局坐标 → BoardGeometry 找格子` 这条路。
  格子尺寸、贴图规格、缩放规则见 [`ART.md`](ART.md) §2、§5。
- **相机里已经踩过的一个坑**：`Viewport.zoomAt` 反解新平移量时**不能减
  `offsetX()`**——`offsetX()` 里含 `panX`，而 `panX` 正是这一步要求的东西，
  减了等于把**上一个**平移量算两遍。表现是「放大 → 拖到边上 → 再捏」时
  画面先闪回中间才开始缩放。要用不含 pan 的 `centredOffsetX()`。
  这个错在「没拖过就捏」的情况下完全看不出来（旧 pan 是 0），
  所以**测焦点缩放的用例必须从"已经拖过"的状态开始**，
  `ViewportTest` 里那两条回归测试就是这么写的。
- **战场固定 80 列 × 36 行**（`BoardGeometry.COLS` / `ROWS`），所有设备一样。
  **2026-09-27 从 40 × 18 翻倍**：原来可建区只有 33 × 18 格，摆几座塔就满了；
  现在 66 × 36 = 2376 格可建、整个战场 2880 格。三段地形按列数一起翻倍
  （通道 4→8、可建 33→66、山区 3→6），各段占战场宽的比例因此没变
  ——**可建区要的是格数，另外两段要的是占比**，理由见 [`ART.md`](ART.md) §5。
  **格子大小只由屏幕高度算，除数是"一屏的行数"`SCREEN_ROWS` 而不是 `ROWS`**。
  这两个数**翻倍那会儿是 18 和 36，当天晚些时候都变成 36**——
  中间那半天里"翻倍不重出素材"成立（格子 27.4dp 没变、纵向要拖）；
  压完界面、`SCREEN_ROWS` 提到 36 之后**格子掉到 15.8dp（53.2px）**，
  纵向重新一屏看全，横向手机一屏 23.7 列、80 格 = **3.4 屏**。
  **代价全落在格子大小上**，素材也**确实偏大了**（`spriteScale` 只剩 0.17–0.22，
  按 128px/格 重出能省一半内存，**还没做**）。
  这个取舍的理由写在 `BoardGeometry.COLS` / `SCREEN_ROWS` 的注释里：
  漏看一路等于漏掉整局，横向看不全只是多拖两步；纵向一屏看得见全部 36 行，
  "哪条路告急要随时能看见"这条**比翻倍之前更彻底**了。
  想回到 26dp 那档只有一条路：把 `ROWS` 减回 18。
- **贴图接上了：两种塔（各三级）、城墙、核心（三级）、敌人都是真图**（2026-09-26/27）。
  四种建筑全画完了，`drawBlock(...)` 那条色块兜底**暂时走不到**，但留着——
  它是"新加一种建筑、图还没画"时的中间态。

  美术是一张张补上来的，中间态要能跑。图的宽高比在构造函数里按设计尺寸校一遍，
  对不上当场抛；色块那边的尺寸和锚点本来就按真贴图规格画的，所以换图不动布局。

- **敌人也换上真贴图了：三张方图，三种兵共用**（2026-09-27）。
  原图交付的是**同一个人的三个动作**——迈步走（脚下带扬起的土）、抡键盘砸
  （甩出一道青电弧）、站着不动，正好对上引擎已有的三个状态，所以
  `game/view/EnemySprites` 就三张 422×422 的图，一种兵一张都不用多。
  - **"三种兵长得一样"不是偷懒，是原图就是这样**。三张贴图分不出杂兵 / 快兵 /
    重甲，所以区分改由两件事承担：**体格**（`EnemyType.bodyCells`，三种差 1.56 倍，
    直接乘在贴图矩形上）和**脚下那圈颜色**（深色接地影 + 一圈种类色的边）。
    `colors.xml` 里那三个敌人色**没删**，是从"填满身体"改成"垫在脚底"了——
    给一张几百种颜色的像素画整体染色会糊成一团，垫在脚下既保住画，又顺手当了接地影。
    真机验过三种色都认得出（红 2722px / 黄 1071px / 紫 174px）。
  - **画布是正方形、边长只有一个合法值**（422px = 体格 1.25 × 1.32 格 × 256）。
    这是拿"整体被缩放了一档"这类错误没办法的办法：等比缩放不改变宽高比，
    `BuildingSprites` 那种校比例的做法查不出来，方画布把边长卡死就查得出来。
  - **走路按"走过几格"翻帧，不按时间**：走 0.7 格换一帧，所以快兵步频快、
    慢兵步频慢，脚不打滑；按时间翻的话三种兵会同一个步频平移，快兵看着像在滑板。
    啃建筑的挥击则相反，**按本机时钟**（0.62 秒一轮，前 62% 抡下去、后 38% 收势），
    因为"啃了多久"是观感不是玩法。
  - **"走过几格"这个数是引擎记的（`Enemy.travelled`），不是 `enemy.x`。**
    第一版图省事直接拿了 `enemy.x`，看着够用——x 一直在涨，走路也确实主要往右走。
    上了真机才看出来：**敌人拐弯是竖着走的**，那几格 `x` 一动不动，于是整只敌人
    平移着上去、腿一下都不迈。所以加了一个只增不减的**路程**字段，
    记在 `Battlefield.stepToward` 里——那是全项目唯一一处改敌人坐标的地方，
    横着走、竖着走、斜着拐弯都在那儿，记一份就全对了。
    拿 `x + y` 之类凑一个数不行：拐弯那一段是斜着过去的（朝的是下一格的中心），
    两个坐标同时涨，凑出来的数涨得比真路程快。
    演示场面的实测（60fps，三个种子）：**纯纵向的帧一共 1848 帧，
    按 `x` 翻帧 0 次、按 `travelled` 翻帧 38 次**——差的就是这一段。
  - **挥击是本机时钟、走路是引擎字段，两个动画都不新增计时器**：
    引擎本来就只给得出"卡住了"（`Enemy.blocked`），给不出"啃到第几口"，
    所以挥击只能挂在时钟上；走路挂在路程上，一分钱时钟都不用花。
    这一版引擎只多了 `travelled` 一个字段（+3 个测试），玩法逻辑一行没改。
  - **没有做**：敌人之间仍然不互相挡（汇到缺口会叠成一坨），
    这是从第一天就定下的取舍，没变。

    草叶的高光（接近白的黄绿）乘上"红不压、绿蓝都压"的系数之后红就冒出来了。

    铺开，色相整个丢掉只留明暗，出来是一条土色的路，草叶的细纹正好当碎石感。

    "这一片该有多亮"，把图按它拉平，格间起伏 1.7% → 0.5%（第一版那张实拍照是
    10.4% → 3.2%——原图越不均匀，这一步越要紧）。

    （第一版下标取模写错、窗口绕成负数，压完起伏反而涨到 127%）。

    有一个（alpha 49），算进去边界框从 775px 变 901px、缩完差 42% 还偏心 54px。
    现在 `content_box()` 要求一行/一列至少 3 个不透明像素，四个抠图脚本共用。
- **战斗已经做完并真机验过**：`Battlefield.advance` 一帧四步——塔开火、子弹飞、
  敌人移动、清场。敌人被挡住就啃挡它的那一座，啃穿的建筑当帧就从场上和占位表里消失。
  三种敌人（杂兵 / 快兵 / 重甲）数值在 `EnemyType`，颜色和体格在 `colors.xml`
  和 `EnemyType.bodyCells`——**体格同时是判定用的身位**（射程判"圈碰到身子"、
  挡路判"身体边缘碰到"），画的和判的是同一个数。
- **塔打的是子弹，不再是持续照射**（`game/engine/Projectile.java`，2026-09-25 加）。
  伤害从"每秒扣多少点"变成"每发多少 + 几秒一发"：
  `BuildingStats.damagePerShot`（当时是 14/18/21）× `fireIntervalSeconds`（当时是 1.0/0.9/0.75），
  **两个数除一下正好是原来那三个每秒伤害**（14/20/28），所以平衡没动，
  （**当天晚些时候这两个数又一起改成了 24/31/38 × 1.6/1.5/1.35**，
  每秒伤害仍然没动，见下面"大炮改手感"那条。）
  动的是观感：出膛和掉血之间多了一个看得见的过程。
  子弹飞 9 格/秒，弩车最远那一格（4.0）0.44 秒到；真机上连拍 12 帧有 3 帧能扫到子弹
  （0.25 秒 ÷ 1 秒，和算出来的占空比一样），直径 26.6px = `SHOT_CELLS` 0.3 格。
  **大炮那边完全是另一回事**（2026-09-27）：它打的是十到二十格，一发要飞
  **一点一到二点二秒**，而装填只有一秒——所以场上<b>常驻有两三发炮弹同时在天上</b>。
  那不是 bug，是"曲射"这件事的代价：二十格外的那只，你按下升级到它掉血之间隔两秒。
  **子弹是追着目标打的**，不是朝一个方向飞出去：敌人现在会拐弯（`PathField`），
  固定方向的子弹会在它换行那几帧擦身而过，而"差一点没打中"玩家既控制不了、
  也没法手算。追着打的前提是<b>子弹比最快的敌人快得多</b>（9 对快兵 1.6），
  这条硬要求写在 `PROJECTILE_SPEED_CELLS_PER_SEC` 里，`ProjectileTest` 盯着它。
  目标半路死了，子弹把剩下的路飞完再消失（不凭空不见）。
  **扣不扣血看是哪种弹**（2026-09-27 溅射接上之后）：
  弩箭不扣血（{@code lands()} 是假），**炮弹照炸**——它结算的是"落点周围有谁"，
  跟当初瞄的是谁已经没关系了。分岔就在 `Projectile.splashCells` 那一个数上
  （0 走老路，大于 0 走 `Battlefield.splash`）。这条当初写在注释里的
  "以后加溅射的位置"，现在就是那两行。
- **"天上已经有几发"要算进挑目标里**（`Battlefield.damageInFlightAt`）。
  少了这一问，六座塔会在同一帧对着同一只 28 血的快兵各吐一发：前两发打死、
  后四发全打空。有了它，塔挑目标时会先看"这一只是不是已经被安排掉了"，
  火力自己铺开——**一座塔看不出区别，五座塔一起打一波时全靠这一条**。
  顺带一个反直觉的结论：**"打空"其实造不出来**。每座塔开火前都要求
  "剩余血量 > 天上已有的伤害"，所以一只敌人一定是被最后落地的那一发打死的，
  天上不会有跟着白飞的子弹。`BattlefieldTest` 里那条"子弹落地时目标已经不在"
  是纯防守性的（测试里得直接把血按到 0 才造得出那个局面）。
- **塔打"最靠前"的那只，敌人去"最近的建筑"、咬"挨着最近"的那座**（2026-09-25 定）。
  这两条是<b>分开</b>定的，别当成一对对称的规则：
  - 塔：挑射程内**寻路表上离核心最近**的那只（`frontmostInRange`）。
    "最靠前"按表算，**不按 x**——敌人会绕路，一只拐到上面去的可能 x 更小
    而其实更接近核心。"打离自己最近的那只"试过一版，又改回来了，理由是
    **实测**：20 个种子的演示场面里"最靠前"守住 6 个、"就近"只守住 3 个
    （那时敌人还是"一路奔核心"，见下面配平那节的表）。差距不大，但方向是稳的。
    代价是纵向错开时塔会越过贴脸的那只去打斜对面的，看着像装看不见——
    但塔防里"该拦的那只多走几步"就是漏怪，这个代价比画面别扭大。
    （`aTowerShootsTheEnemyFurthestAlongNotTheNearestOne`，两只敌人特意摆成
    "一只在靠近、一只已经走过去"，两种规则才分得开。）
  - 敌人：**去的方向和咬谁都是"最近的建筑"**，塔和核心**优先级相同**
    （2026-09-25 改）。寻路表的目标集合是**所有塔 + 核心**（`Battlefield.isTarget`），
    墙不在里面——所以一座塔只要比核心近，敌人就是冲着塔来的，会绕路过去拆。
    **核心不再是天然终点**，"把敌人放进来让它们打塔"这件事以前根本不存在。
    停下来之后咬谁见下一条 `nearestBite`。
    - 这一条是用户提的那个问题的落点："敌人明明贴着塔，为什么还是奔核心去"。
      根因是**结构上的不对称**：从前目标是核心一个，塔只是"很贵的地"。
      修法不是调数值，是把塔也放进目标集合。
    - 表里因此有**两张**：`path`（所有塔 + 核心，管去哪儿）和 `corePath`
      （只有核心，管"谁最靠前"）。分两张是因为问的不是一件事——
      用 `path` 算进度的话，站在塔跟前啃塔的那些数值特别小、看着最"靠前"，
      塔就会集体去招呼它们，真正逼近核心的那只反而没人管。
    - **玩法后果：墙挡不住一个"目标是塔"的敌人，只能拖住它。**
      一座塔背后砌一格墙是没用的——敌人从旁边绕过去照样啃塔（
      `aTowerRightBehindAWallStillShootsWhatIsChewingIt` 的注释里记了这件事，
      那条测试因此得把墙砌成一整列才逼得出"啃墙"这个局面）。
      要把塔保住就得把通往它的路整个封上。
  - `progressOf` 的两个分支**方向必须一致**（有核心走 `corePath`，没核心退回
    "离右边界多远"）。写反了只在**场上没核心**时发作，正常对局永远走不到那一支，
    所以两条测试一条带核心、一条不带，合起来才盖全。
- **墙是唯一的例外。** 塔从来不把墙当目标（它本来就只打敌人）；
  敌人**只在寻路表真的指进墙里时才拆墙**，顺手够得着的墙不咬。
  少了后半条，重甲（身位 1.25，比杂兵宽）会放着挡在面前的塔不啃、
  转身去啃旁边那面没挡路的墙。所以**敌人那边的**候选里，墙只有站在 `blocker` 那一格
  （= 寻路表指着它 = 绕不过去）时才算数（`anEnemyBitesTheNearestBuildingButNeverAWallThatIsNotInItsWay`）。
- **绕墙、拆塔**（2026-09-25 改定，现在是"墙贵、塔和核心都是目的地"）。
  同一个位置换一种建筑，敌人的反应要分开：
  - **墙**：`BuildingStats.WALL_PATH_COST = 4096`（翻倍前比整块战场 720 格加起来
    还大，余量 5.7 倍；**2026-09-27 战场变成 2880 格之后这个常量没动，余量缩到
    1.4 倍**——仍然比任何绕路都贵，但不再是压倒性的。**再动战场尺寸时这条要一起看**）
    → 任何绕路都比穿墙便宜 → **绕**。只有真的封死、绕不过去，表上的箭头才会
    指进墙里，敌人才动手拆（`Battlefield.stepCost` 是唯一的价钱表）。
  - **塔和核心**：**不参与价钱计算**，它们是寻路表的**目标**，那几格恒为 0
    → 箭头本来就指着它们 → 走过去，发现占着，**拆**。
  - 所以"拆塔"不再需要一个"塔很便宜"的数。**上一版那个按类型分的价钱表
    （`BuildingStats.pathCost`）已经删了**：塔进了目标集合之后，给塔的那一档
    （先后试过 20 和 1）是死代码——没有任何一处读得到它。留下 `WALL_PATH_COST`
    一个公开常量，`PathFieldTest.uniform()` 也用它。
  - **那个"塔价 20"是我算错了给出来的**（凭感觉说"有点贵"，量出来才发现分界是 3）。
    量法记在这儿：塔占 2×2 压住一条道时，绕过去多走 4 步，穿过去多花 `2 × 塔价`，
    所以"拆"的条件是 `塔价 < 3`——实测 2 拆、3 绕。**但那个分界跟着地形走**
    （塔贴着墙或夹在一格宽的走廊里，绕路可能只要 +2，分界就掉到 2 以下），
    于是同一个"塔价 2"，有的地方拆、有的地方绕，玩家看到的是"这两座明明一样摆，
    敌人只拆左边那座"。取 1 才没有这个问题。**这一段留着是因为它解释了为什么
    现在干脆不走价钱这条路**。
  - 代价是**摆在敌人道上的塔会被啃**——以前塔是绝对安全的。
    这是这条改动真正的玩法后果，演示场面那四座塔正好压在道上，见下面配平那节。
- **装填计时是"减 dt、开火时再加回去"**，不是"开火时赋值成间隔"。赋值会每发白丢
  一帧的时间（0.05 ÷ 1.0 = 5%），结果就是**帧率决定难易**：同一条路配同样的塔，
  60Hz 的手机守得住、120Hz 的守不住，而这种事在真机上基本查不出来。
  空闲时还要把负数夹回 0（不然一只敌人在圈外等了三秒，塔一进圈就补发三发，
  看着像卡了一下）。`BattlefieldTest.theFireRateDoesNotDependOnTheFrameRate`
  用两种帧长跑同一段时间，比挨的伤害。
- **画面上那层"塔→目标"的连线没了，改成画子弹本身**（`BattlefieldView.drawProjectiles`）。
  连线说不了"打出去的东西还没到"，于是敌人掉血看着像凭空发生；子弹能。
  **换真贴图只动 `drawProjectiles` 一处**：把那个 `drawCircle` 换成 `drawBitmap`、
  圆心对准 `(x, y)` 就行，尺寸见 `SHOT_CELLS`（规格已写进 [`ART.md`](ART.md) §4），
  引擎一个字都不用改——它只知道"有一颗子弹在这个坐标上"。
  **帧闸门也跟着改了**（`BattlefieldView.tick`）：判断"还要不要下一帧"从前只看
  "场上还有没有敌人"，现在还要看"天上还有没有子弹"。不改的话最后一波清空的那一刻
  画面就停了，**还在飞的那几发会僵在半路**（而且以后一直挂在那儿）。
- **敌人会自己找路去最近的建筑**（`game/engine/PathField.java`，2026-09-25 加）。
  从目标集合往外铺一张 Dijkstra 的"还有多远"表，敌人每帧只问一句"四邻里哪格更近"，
  所以**墙不是墙、是"很贵的地"**（空地 1、墙 4096、塔和核心是目标）：有缺口就绕缺口，
  围死了才动手拆。绕和拆因此不是两套规则，是同一张表在两种地形下的两个结果。
  表只在**建筑变了**的时候重铺（`place` / `remove` / `move` / `clear` → `pathDirty`），
  不是每帧。
  **这条改动修掉了一个"这一局根本输不了"的 bug**：从前敌人只直着走，而核心只占
  3 行（第 7–9 行），18 条路里只有那 3 条的敌人会撞上核心，其余 15 条的敌人一路走出
  右边缘——只记一笔漏怪，**核心一滴血都不掉**。五波打完永远算守住。
  （这里的 **18 条路、第 7–9 行都是 2026-09-25 当时那张 40×18 的棋盘**上的数；
  2026-09-27 翻倍之后是 36 条路，核心也不在那几行了。**这条 bug 本身和棋盘多大
  无关**——只要核心占的行数远少于总行数，"直着走"那版就一定漏得掉。）
  现在敌人会拐弯，任何一行的敌人都摸得到核心，[`Outcome.OVERRUN`] 才是真的输。
  代价是敌人**全部汇到缺口和核心跟前**，于是下面那条"互相不挡"变得显眼得多。

  （大纲 §1 / §7 和 15 页幻灯片都按这个口径改过了，草图和 `fig_*` 里统计页排在最前面、
  agent 圆钮也画在统计页上）。
  **连带的一条：agent 的入口放在统计页上**，不放游戏里——它要回答的问题
  （"这个月怎么花了这么多"）答案就在那一页上，人在哪儿问、证据就该在哪儿。
  所以 `ui/` 里那一页的正式名字是 **dashboard / 统计**，不是"游戏旁边的第二屏"。

  落地页**没有第二个开关**——它<b>就是</b> `menu/bottom_nav.xml` 里的第一项
  （`BottomNavigationView` 默认选中第一项，`MainActivity.showTab` 再照它刷一遍
  界面）。想换主页就去换那个文件里的顺序，`MainActivity` 一个字都不用改。
  反过来说：**那个文件里第一项是谁，谁就是主页**，两处不要各写一份。

  | 谁 | 干什么 |
  | --- | --- |
  | `@id/game_page` | 游戏页 = HUD + `@id/play_area` + 操作行。三段包在<b>一个</b> `LinearLayout` 里，切页时一口气藏掉 |
  | `@id/empty_page` | 另外三页<b>共用</b>的空壳，一句 `Xxx is not built yet`（`nav_not_built`），文案由 `showTab` 现填 |
  | `MainActivity.showTab` | 切页。只动可见性，不 new 任何东西 |

  **四个坑**：
  ① `game_page` 和 `empty_page` 是兄弟、weight 各 1，**"上面固定、中间吃剩余、
  下面固定"这三段必须留在同一个 LinearLayout 里**——拆成三个兄弟去和 empty_page
  抢高度的话，战场会算出错误的高度，格子尺寸跟着错；
  ② **世界层（`battlefield`）也得跟着藏**：它铺满全屏、画在界面层下面，而空壳是
  透明的（底该是同一片岩石），不藏的话统计页上会透出一整个战场。
  藏它用 `INVISIBLE` 不用 `GONE`——`GONE` 量不出尺寸，格子几何和相机就得在切回来时
  整个重算，中间那一帧还是 0×0 的，取景会跳一下。**岩石底（`background`）不藏**：
  四页站在同一片地上；
  ③ **菜单第一项在 `setOnItemSelectedListener` 挂上之前就已经是选中态了**，
  那一次不会回调过来，落地页得在 `setUpBottomNav` 末尾自己刷一遍——不刷就停在
  布局文件里那个"game_page VISIBLE"的初始状态上，和导航栏亮着的标签对不上；
  ④ **切走等于暂停，这是白捡的、不是设计出来的**：整场战斗的推进
  （`Battlefield.advance`）挂在 `BattlefieldView.onDraw` 的 `tick` 里，
  而 `INVISIBLE` 的视图不会有 `onDraw`——敌人、子弹、波次计时器全冻在原地。
  回来也不补帧（攒下的时间被 `MAX_FRAME_SECONDS` 0.05 秒一刀切掉），
  所以来回切不会一回到游戏就发现敌人已经走过半个屏幕。
  好处是玩到一半去看统计不会输，但它**不是**一个暂停功能（没有暂停图标、
  暂停时也不能操作）。真要做暂停，得从引擎那层停（别再喂 dt），
  而不是靠"这一页看不见"——那是碰巧。

- **点建筑 = 看它，不是接着放**（2026-09-25 改的）。规则和部落冲突一样：

  **2026-09-27：详情从"一个弹窗包办"拆成"场上一条操作条 + 一张只读表"。**
  拆的理由不是好看，是**模态**：`BottomSheetDialog` 开着的时候整个战场收不到
  触摸（点在面板外面只会把面板关掉），于是"点一下建筑、直接拖着它走"这条手感
  根本做不出来——手指按在建筑上，事件却落在窗上，玩家看到的是屏幕在滑。
  拆开之后动词（详情 / 升级 / 整排 / 拖动）全在场上那条**非模态**的条子上，
  读数（等级 / 占地 / 耐久 / 射程）留给铺得开的底部弹窗。

  两个直接后果，都是必须的：

  - **条子不是 `BottomSheetDialog`，是 `@id/play_area` 里的一个普通 View。**
    它只吃掉自己那一小块，别处照样归战场。位置由 `MainActivity.placeBuildingBar()`
    按选中那一座现算（`inspectedBounds` + 夹回面板内），**不给它设 elevation**
    ——投影画出来是个矩形轮廓，在一整片地上是条硬线（同 `@id/play_area` 那段）；
  - **弹窗 dismiss 时不再撤销选中。**原来"撤高亮"挂在 `setOnDismissListener` 上；
    现在那条路会让"看完数值随手一关"把操作条和金光一起带走——而玩家下一步
    多半正是想升级或者拖着它走。撤退归 `BattlefieldView`：点一下空地才"没在看谁了"。

  **升级价只算一遍。**详情表上那一行价和 `upgradeInspected` 真扣的钱，
  读的是同一对 `upgradeTotal` / `upgradableCount`；各算一遍迟早会算岔，
  而"表上说 45、扣了 90"是玩家一定会发现的 bug。

  **升级价从条子上搬到了详情表里**（当晚条子换成图标方框之后）：屏幕上唯一
  写着价钱的地方没了，所以 `sheet_building.xml` 多一行 `@id/bld_cost`。
  **删一处必须补一处**——不补的话玩家按下去只会收到"资源不够"，
  却无处可查差多少。到顶那行写 "Max level" 而不是整行 GONE：
  藏起来的话分不清"没有下一级"和"这一屏不显示价钱"。

  **升级那个框到顶了也不禁用**，改成点一下弹一句 "Max level"。禁用等于
  "按下去什么都不发生"，而那和"我没点到"在屏幕上是同一件事——
  三个长得一样的方框里挑一个按下去没反应，玩家会去怀疑是框坏了。

  **八个坑**：① 升级价的"不能升"必须是 `null`，**不能是零元的 `Cost`**——
  "到顶了"和"免费升"在界面上长得一样，混起来满级那座建筑的升级按钮会一直亮着、
  点下去不掉钱也不升级（`CostTest` 盯着这条）；② **范围圈的数值单位是格不是像素**，
  画的时候才乘 `BoardGeometry.cellPx()`，不然放大缩小时圈不跟着地走；
  ③ 范围圈**不要用 `game_ok` 那个绿**——绿在这个界面里已经固定表示"这一下能放"，
  两个意思共用一个颜色，玩家会以为圈里圈外是能不能建的区别（用 `game_range`）；
  ④ 范围圈画在建筑**底下**（`drawSprites` 之前），盖在上面会把塔糊掉；
  **选中高亮只描边、不填色**（`NO_FILL = 0`）——填色和它底下那个范围圈
  叠成两层半透明，真机上把青色的塔糊成了橄榄色；贴图接上之后任何一层填色
  都是盖在美术上的脏东西。"选中"让金边一个圆去说就够了；
  ⑤ **挪动是"改坐标"，不是"拆了重放"**（这一条踩过）：`moveCore` 原来是
  `remove` 再 `place`，会新建一个 `Building`——`level` 回 1，而且所有拿着旧引用的
  地方（详情面板、战场高亮）都变成指向一座已经不在场上的建筑。现在一律走
  `Battlefield.move`（底层是包内可见的 `Building.relocateTo`，只有它能调），
  **等级和引用都带得走**，`BattlefieldTest.movingATowerCarriesItsLevelAlong` 盯着；
  ⑥ 收起高亮要挂在 `setOnDismissListener` 上，**不能挂在 Close 按钮上**：
  底部弹窗有三种关法（按钮、下滑、点面板外面），挂按钮上后两种关完
  地上那个金圈还亮着，看着像"还选着它"但已经没有面板能操作它了（真机上撞到过）；
  ⑦ `move` 里要**先还旧格子、再占新格子**：反过来的话，新旧占地重叠的那几格
  （比如往右挪一格）会被当成"被自己占着"，于是"挪一格"永远失败——而玩家
  只会看到红闪一下、不知道为什么。`nudgingATowerByOneCellWorks` 盯着；
  ⑧ 挪不过去时**留在挪动模式**，不要退回普通模式：想挪到墙边，手指点歪半格
  是常事，点歪一次就得回详情面板重新点一遍 Move 的话这个功能没法用。
  同理，正在挪的那一座**要一直亮着金边和范围圈**（`drawRanges` / `drawOverlay`），
  只在手指按着的时候画虚影是不够的——手指一抬屏幕上就没有任何东西说明
  "挪的是哪一座、它原来在哪儿"，玩家得自己记。

  **2026-09-27（当天更晚）：操作条上的文字全换成图标，大炮改了一次手感。**

  两件事一起做的，因为它们都指向"这一屏上少写点字"。

  - **三个方框。**条子原来是"标题 + 三个文字按钮 + 一句提示"，真机上量出来的
    毛病是升级按钮那串价（`"Upgrade · Cache 20 + Output 8"`）太长、换行之后
    把整条撑到接近满屏宽（1260px 的屏上占了约 1214px），浮在战场上挡掉一大片地。
    改成 40dp 见方、**只有图标**的三个框（`ic_bar_info` / `ic_bar_upgrade` /
    `ic_bar_row`），贴在建筑**下沿**（原来是上沿）——手指点在建筑上，
    建筑上面那一片才是玩家正在看的地。
    - **固定的尺寸顺带修掉了一个隐患**：文字版里条子宽度跟着文案变，
      而它每帧都要跟着相机重算位置（`placeBuildingBar`），
      `barMeasured` 那个缓存每次改字都得作废。图标版只有"整排"那一格
      显示/隐藏会改宽度，所以那一处才需要失效；
    - **图标不是可选的**：三个框没有文字，不给 `contentDescription` 的话
      读屏念出来三个都是"按钮"。价钱挪进升级框的 contentDescription，
      **那是屏幕上唯一看不见它的地方**，而看不见代价的按钮对谁都不该按；
    - **"整排"那个图标跟着状态换**（`ic_bar_row` ↔ `ic_bar_single`），
      两个 drawable 的条宽和位置是对齐的，所以换的时候画面不跳。
  - **大炮：张角 30° → 60°，单发 14/18/21 → 24/31/38，装填 1.0/0.9/0.75 →
    1.6/1.5/1.35 秒。**后两个数是**同一次改动、方向相反**，
    除一下每秒伤害几乎没动（14/20/28 → 15.0/20.7/28.1）——**这是有意的**：
    张角翻倍已经把覆盖面积白白翻了一倍，再把 DPS 抬上去，这门炮就成了
    "又远又宽又疼"。（`CostTest.theCannonTradesRateForWeightWithoutGainingDps`
    把这三条边钉住：单发够重、节奏够慢、DPS 还是原来那一档。）
    新数字和敌人血量的关系：一级 24 点**打不死快兵**（28 血，剩 4 点），
    二级 31 点刚好一发带走它，三级 38 点仍然轻于弩车任何一级（34/45/58）。
    - **两个真机后果**：二十格处的半宽从 5.4 格变成 11.5 格，所以**摆位宽松多了**
      （"对准某一条缝"退回"摆在这一侧就行"）——它现在几乎不挑位置，
      这是拿"好摆"换"好瞄准"，还没有重新配平；
    - **测试跟着动的三处**（改数值时必须回来核）：
      `theCannonFiresThroughATenToTwentyCellWedge` 写死半角 30° 和"六分之一"；
      `theFireArcCatchesExactlyWhatTouchesIt` 里那条角度边用的是 `10 × tan30°`；
      `theCannonIgnoresWhatIsOffToTheSideOfItsWedge` 里那只"射界外"的敌人
      **从第 10 行挪到了第 14 行**——23° 在 30° 的半角下已经落在射界**里面**了。
      这最后一条是这类测试最阴的地方：写死的角度一旦比真实张角还宽，
      它就永远绿，什么也验不到。

  **范围圈和真实判定是同一个数**（2026-09-25 战斗做完之后）：
  画的和判的走同一个 `BuildingStats.fireArc(type, level)`——2026-09-27 之前
  是一个 `rangeCells` 半径，现在是一个 `FireArc`（内径 / 外径 / 半角 / 溅射）。
  **做成一个值对象的理由就是这条**：射界现在是四个数，拆开摆的话
  任何一个调用点都可能只读了三个（漏掉内径 = 十格盲区静悄悄地没了，
  漏掉半角 = 变成整圆），而这两种错都不会让任何东西报错。
  判定额外加敌人的半个身位（`EnemyType.halfBodyCells()`——体格是逐只的，
  重甲比杂兵宽，所以它从更远处就开始挨打）——因为圈是"离我 N 格以内"，
  而敌人的判定点是中心，不加的话半个身子在圈里的反而不挨打。
  墙后紧贴的那座弩车（差 0.05 格）就是这么救回来的，`BattlefieldTest` 里钉着这一条。
- **三种建筑都能升级**（2026-09-25 改的）。从前只有塔能升，墙和核心的
  `BuildingStats.upgradeCost` 直接返回 `null`；现在墙和核心也按级涨耐久
  （墙 150/220/320、核心 600/900/1300），于是那张表里
  **`null` 只剩一个意思：到顶了**，界面上也就不用再解释"这种建筑这个版本还不能升"
  ——那句文案和那个分支一起删了，留着就是一句永远显示不出来的话。
  升级吃哪种资源和建造价保持一致（塔 CACHE + OUTPUT、墙只吃 INPUT），
  因为三种资源不通兑，"造得起、升不起"是说不清的局面，`CostTest` 盯着这条对应关系。
  核心升级**故意和塔抢同一种资源**，还比塔贵：加厚核心是"承认自己会漏"，
  再摆一座塔是"争取不漏"，这个取舍是真的，所以核心升级不该是不要 OUTPUT 的便宜事。
  界面上"到顶了"那一条不变（按钮换成点不动的 Max level）。
- **详情面板上多了一行耐久**（`bld_hp`，2026-09-25 加的）。塔、墙、核心都有血，
  所以这一行不像攻击范围那样会整行 GONE。以前模型里三种建筑明明都有耐久，
  界面上却一处都不显示——"墙是有血的"这件事玩家根本看不出来，
  被打之前它看起来和装饰没区别。胶囊的圆点用血条那个绿（`game_hp_good`），
  和战场上那条血条同色：面板上的数字和地上那条杠说的是同一件事。
- **建筑可以直接拖着走**（2026-09-25 加的搬动，**2026-09-27 起改成一拖就走**）。
  和部落冲突一样：摆错了随时能改，**不花钱**，也不经过商店。
  这一条是"摆位是这游戏唯一的策略动作"的地基——只能一次性摆对的话，
  没人敢在开局就下手。

  **没有 Move 按钮了。**点一下建筑冒出操作条，手指就在建筑上，
  直接拖（`drag = RELOCATE`）。原来的"先按 Move 进挪动模式，再点目标格"
  是两步，而且中间面板一消失玩家会以为点了个"关掉"。

  > **落点怎么算，2026-09-27 晚些时候改过一次。**这一版写的是"从手指底下算"
  > （`board.topLeftFor` 的吸附），当天晚上换成了**按手指走了几格算**
  > （`carryDCol`），连"建筑跟着手指走"一起补的——为什么换、
  > 吸附式会怎么跳，见下面那条「把"建筑跟着手指走"补上了」。

  > **那句 "Drag to move" 在 2026-09-27 晚些时候没了**：条子换成三个图标方框之后
  > 上面不再有文字。所以**这个手势现在没有任何文案在教**，靠的是选中时那圈金边
  > 和"手指本来就压在建筑上"这个位置关系。要是真机试用时没人试得出来，
  > 该补的是**一句一次性的提示**（第一次选中时弹一句），而不是把文字塞回方框上
  > ——那正是这次要拆掉的东西。

  拖完只有两种结果：**挪过去**（退出拖动，选中和条子都留在新位置——
  下一个动作十有八九是接着看它）、**挪不过去**（红闪 + 一句话，
  停在原地）。手指没怎么动就松开时落点还是它自己，`handleMoveTap` 那一支
  会把它 inspect 回来，等于什么都没发生。

  | 谁 | 干什么 |
  | --- | --- |
  | `Battlefield.move` / `moveAll` + `Building.relocateTo` | 挪任意一座建筑、或一整排。**不花钱**，所以这条路不经过 `BuildGate`；**改坐标不是拆了重放**，`level` 带得走（坑 ⑤）。"挪一排"走 `moveAll`，单座是它只有一个元素时的特例 |
  | `BattlefieldView.handleMoveTap` | 拖动的落点判定。**点一下和拖一下走的是同一个方法**：对引擎来说"拖到哪儿"和"点到哪儿"是同一件事，分成两套只会让两条路落到不同的格子 |
  | `BattlefieldView.relocatingGroup()` | 这一下要挪哪一批。有 `movingGroup` 就用它，没有就用 `selection`——现在实际生效的是后者 |
  | `BattlefieldView.forceSelection` | 挪完把选中还回去。**必须走这个，不能走 `setSelection`**：建筑位置变了但批次没变，`setSelection` 的"没变就不通知"短路会直接返回，外面收不到通知、操作条就留在原地不跟着搬 |
  | `BattlefieldView.ghostType` / `ghostLevel` | 虚影是谁、按几级算。**虚影有两个来路**（要放新的 / 要挪旧的），画虚影的三处都靠这两个方法，别各写一遍三目 |

  **挪动那条路和 `BuildGate` 无关**：那个关卡问的是"这件买得起吗"，而挪动不产生
  任何开销，所以 `updateMoveGhost` 里没有 `affordable` 这一问，界面也别给它加
  变暗逻辑（加了玩家会以为挪不起）。同理，挪不过去的提示是
  `bld_move_blocked`（只说位置），不是 `shop_need_more`（说钱）——
  借错那句话会把玩家引到钱包上去，而问题其实在位置。

  **已知冗余**：商店里选 Core 那条路（`BattlefieldView.movingCore`）现在和新功能
  重复了——"选中核心这一类点哪儿挪哪儿"和"指定这一座点哪儿挪哪儿"是同一件事。
  留着是因为商店里那行文案（`shop_size_core`："move the one you have"）已经把
  那条路讲给玩家了，删掉会让那句话落空。要收的话两处得一起收。
- **选中整排、拖出一排、拖着一排走**（2026-09-27）。四件事一起做的，
  因为它们共用一套"手指下的东西是一整排而不是一座"的状态：

  1. **点两下扩成整排**：第一下还是老样子（看一座），第二下把选中的范围
     扩成那一座所在的整排——**竖排优先，没有竖排才选横排**；
  2. **整排一起升级**：每座各涨一级，到顶的跳过，**资源不够就一座都不升**（全部或全不）；
  3. **整排一起挪**：挪动模式下不管点还是拖，动的都是整排，而且**要么整排挪过去、
     要么整排都不动**；
  4. **拖一下就建一排**：手上拎着东西时，点空地建一座，**从空地拖出去就建一排**。

  | 谁 | 干什么 |
  | --- | --- |
  | `Battlefield.lineOf` | 一座建筑所在的那一整排：同类型 + **首尾相接**的那一串。竖排优先；不比等级（一列墙里有一座升过级了还是那一列） |
  | `Battlefield.moveAll` / `canMoveAll` | 整排一个位移，**原子**。判定那一段单独抽成 `canMoveAll`，给拖动中的虚影用（同 `BuildGate` 的"先问价、后成交"） |
  | `Cost.times(int)` / `Cost.plus(Cost)` | 一次买 N 座的总价 / 一整排各不相同的升级价合起来。**两个都在 `Cost` 上**，别在调用方手搓循环 |
  | `BoardGeometry.runLength(anchor, finger, span)` | 拖出来的这一排有几座。纯整数运算，能单测；建一排和挪一排算的是同一个数 |
  | `BattlefieldView.selectLine` / `selectSingle` | 扩成整排 / 缩回一座。**只有 `setSelection` 一个写入口**，所以外面收到的表就是地上画的那些金边 |
  | `BattlefieldView.Drag` | 这一拖是什么意思（`PAN` / `BUILD` / `RELOCATE`），**按下那一刻定死** |
  | `BattlefieldView.ghostCells` | 虚影的每一块。是**表**不是"头一块 + 步长"：挪一排时那几块不一定等距 |
  | `BattlefieldView.relocatingGroup()` | 这一拖要挪哪一批。两个来路收在一处：`selection`（拖着选中的那座走，现在走的是这条）和 `movingGroup`（旧的"先按 Move 再点目标"那条） |
  | `MainActivity.selection` | 操作条现在管着哪几座。标题、"整排"按钮、总价、Upgrade 全读它 |

  **"整排"是操作条上的一个开关，不是再点一次场上的那座建筑。**
  原来的设计是"再点一下那座建筑就扩成整排"，做不到：条子出现的同时手指已经
  抬起来了，那一下没有谁接得住。所以条子上有一个 `@id/bar_line`
  （"Row ×4" / "Single"），两个方向都走 `BattlefieldView` 那两个入口——
  **外面不自己改 `selection`**，免得条子和地上那些金边说岔。这一排只有一座
  （孤零零一座塔）时整个按钮 GONE：按下去只会选中它自己，那是一句空话。

  **三个 `Drag` 模式按下时就定死**（`beginDrag`），不是拖过一格再判：
  判晚了的话，手指先动的那一格已经被当成平移吃掉了，建筑会先跳一下再跟着手走。
  判定顺序是 **挪动模式 > 手上有东西 > 按在已选中的建筑上 > 拖地图**：

  - **手上有东西盖过一切**（2026-09-27 改）。原来它排在"按在建筑上"后面，
    结果是手里拿着塔、手指落点正好压到已有的建筑上时，这一拖掉进了"拖地图"
    ——玩家想铺一排墙，屏幕却开始滑。按在建筑上本来就放不下，虚影会整条画红，
    比"屏幕莫名其妙滑走"清楚得多；
  - 按在建筑上时，**只有那一座本来就在选中范围里**才是"拖它走"，
    别的时候是在拖地图。少了这一条，想平移视野时手指正好落在塔上，
    塔就被拖走了——而挪动是"放得下就生效"的，玩家会发现阵型莫名其妙变了样。

  **拖出一排 / 挪一排的时候，虚影跟着手指走，不收。**原来是"一开始拖就把虚影
  收起来"（那一拖只可能是平移），现在三个模式里只有 `PAN` 才收。

  **双指拖动是补上的一个缺口。**手上拎着一件东西时单指拖动被"建一排"占掉了，
  没有别的手势能挪地图——想一边拿着货一边把画面挪到要放的地方去就做不到。
  所以第二根手指一按下来就整下改判成"拖地图"（`multiTouch`），**一直管到
  最后一根手指抬走**：中途松开一根之后剩下那根该算"继续拖地图"还是
  "重新开始建一排"是说不清的，索性整下都当拖地图。重心按剩下的手指重算
  （`ACTION_POINTER_UP`），不重算的话下一帧的重心会从两根手指中间直接跳到
  剩下那根上，那一跳会被当成一次平移、画面猛地窜一下。

  **九个坑**：① **"相接"按占地算，不按左上角差几格**——2×2 的塔占 4-5 行、
  下一座在 6 行，看着就是贴着的，所以它们是挨着的。把"挨着"写成"左上角差 2"
  的话一列塔永远选不中；② **竖排优先**：一个 2×2 的方块两条都成立，
  取竖的那条——战场上纵深比宽度金贵，玩家布阵时脑子里那条线是"这一列"；
  ③ `lineOf` **不比等级**：玩家眼里的"一列墙"是摆在那儿的一串，
  不是"一串一样强的"；④ **`moveAll` 判定时必须把整排自己都让开**
  （问的是"占着这格的人是不是自己人"）：一排墙往右挪一格，新格子有一半正是
  邻座的旧格子，不让自己人的话"整体平移"这个最常见的用法会当场判失败；
  ⑤ **`canMoveAll` 和 `moveAll` 必须严格同进同退**：虚影是拿前者决定画绿还是画红，
  它说行、后者说不行的话，玩家看到一块绿框、松手却弹回来，而且不知道为什么
  （`BattlefieldTest.canMoveAllAgreesWithMoveAllOnEveryCase` 盯着）；
  ⑥ **`Cost.plus(Cost)` 和 `Cost.plus(ResourceType, long)` 名字像、语义反着**：
  前者是"两笔账合起来"（逐种相加），后者是"给这一项设个价"（写重了当笔误，
  所以是**改写**）。整排升级的总价必须走前者，写成循环调后者的话，
  五座墙的总价会等于一座墙的价；⑦ **建一排是"能建几座建几座"，
  不整排回滚**：手指拖过一段放不下的地（通道、山区、别人身上）或者钱只够
  前面几座时，前面那一段照建、从第一处不成立断开——和虚影画出来的那截绿边
  一模一样。整排回滚的话，拖过一条通道就得重新拖一次，而玩家看不出是为什么；
  ⑧ **整排升级是全部或全不**：资源只够升其中几座时一座都不升。
  和中途卡住的那半排墙同一个理由——升了三座、剩两座没升，
  玩家自己都记不清哪几座动了，而这一排在他眼里本来是同一样东西；
  ⑨ **放完 / 升完要保住"整排"这个状态**：升级完走
  `refreshSelection()`（只重画），**不能走 `setInspected`**——后者会把整排
  缩回一座，一起升完一排墙之后地上只剩一道金边，玩家会以为刚才只升了一座。

  **已知冗余**（和"建筑可以直接拖着走"那条末尾说的是同一件事）：
  `startMoving(Building)` 现在只剩 `startMovingSelection()` 这一个用途，
  单座那个重载是给它内部用的。留着两个公开入口是因为 `startMoving(null)`
  还要当"取消挪动"用——把签名改成收 `List` 的话，所有 `startMoving(null)`
  的调用点会变成二义（`Building` 和 `List` 两个重载谁接 `null` 都行），编译不过。

  **还有一处冗余是 2026-09-27 新添的**：操作条上的 Move 按钮没了之后，
  "先按 Move 再点目标"那条路（`startMovingSelection` 那个公开入口）在应用里
  **已经没有调用点**——拖动走的是 `selection`。`movingGroup` 那一套
  （`startMovingGroup` / `movingGroup()` / `drawRanges` 和 `drawOverlay` 里
  那两个循环）现在是**够不着**的状态。留着是因为 `handleMoveTap`、
  `updateMoveGhost`、`relocatingGroup` 三条都是两条路共用的，
  合并成一条要动到七八处，而它现在是对的。要收的话这是一处。

  2026-09-27 加完之后 **305 个测试 / 0 失败 / 1 跳过**（原来 279）。
  **这一版没有加测试**：改的全是触摸分发和界面装配（`BattlefieldView`
  的 `beginDrag`/`updateGhost`，`MainActivity` 那条操作条），
  这两处都不在 JVM 单测够得着的范围里——引擎那半边（`moveAll` /
  `canMoveAll` / `lineOf`）在上一版已经测过了，这一版没碰。

  **2026-09-27（同一天，再晚一点）：把"建筑跟着手指走"补上了。**
  用户的原话是「为什么拖动的时候不是建筑随着手指动」——
  **上一版这条功能其实是通的，只是全程没有一个像素跟着手指走**：
  按住一座已选中的塔拖，屏幕上什么也不动，手指一松塔才凭空跳过去。
  三个错叠在一起：

  - **根因是 `ghostType()` 只认两个来路**——`selected`（商店里挑的那一类）
    和 `movingGroup`（详情面板按 Move 那条路）。而"直接拖场上已选中的那一座"
    这条路上**两个都是空的**，于是取到 `null`，`drawOverlay` 和 `drawRanges`
    里那两句 `ghost != null` 全跳过：**占地虚影和射界扇形一块都不画**。
    这是加功能时漏改的一处——新来路加进去了，问"现在拎的是谁"的那个方法
    没跟着认。现在多一个 `carriedAnchor()`，只认 `carrying()` 的那一批。
  - **位移改成"手指走了几格"**（`carryDCol` = 当前格 − 按下那一格），
    不再是 `BoardGeometry.topLeftFor` 的"吸附到手指底下那一格"。
    吸附式在按下的那一瞬间就会算出偏移：抓一座 2×2 塔的**右半边**，
    手指还没动、它已经准备往右跳一格，而且抓左边和抓右边松手落点还不一样。
    按行程算的话按下那一帧必然是 0——塔纹丝不动地等着，挪几格就走几格。
    落点跟着一起改（`commitMoveDrag` 不再复用 `handleMoveTap`），
    不然虚影一路显示"右三格"、松手却落到"右一格"：**预览和结果差一格，
    表现就是塔在抬手那一瞬间自己跳一下**，比原来还怪。
  - **建筑本体画在手上**：`drawSprites` 把它从排序那一轮里摘出来、
    最后画（离地了就不该被谁挡住），平移到落点再抬一格
    （`CARRY_LIFT_CELLS`，抬一格是为了不让指肚盖住它）。地上那块绿/红
    就是落点，悬在上面的贴图是"拎的是谁"——部落冲突里拎起一座建筑的样子。
    跟着一起挪的还有三处：血条、炮口火焰、**悬浮操作条**
    （`inspectedBounds()` 认这个位移，而 `updateMoveGhost` 跨一格就叫一声
    `notifyCameraChanged()`——操作条挂在那个回调上，借它而不是新开一条，
    因为两者要重算的东西完全一样：相机 × 格子 → 屏幕）。

  **顺手补的一个洞**：红闪（放不下时那一闪）原先画的时候才去问
  `ghostType()`，而红闪要亮 0.7 秒——**松手之后手上就空了，一问就是 `null`，
  红闪跟着不画**。拖动这条路上没有 `movingGroup` 兜底，所以"放不下"从来
  只靠一句 toast 说。现在判失败的那一刻把类型记进 `rejectedType`，
  画的时候不再问别人。真机验过：把塔拖到山区上松手，红闪亮在落点、
  toast 说 "The Tower cannot go there"、塔回到原位。

  **真机验过三件事**（`adb shell input motionevent DOWN/MOVE/UP`，
  手指按住不放时截图）：单座塔拖到草地上——贴图悬在落点上方一格、
  绿框在地上、松手正好落在虚影那一格、原位留空（不是复制一座）；
  整排九座墙一起拖——九座一起被拎起来、绿框九块、松手整排落地、
  没选中的那几座一动不动；拖到山区上——红框、松手弹回、红闪 + toast。

  **没跟着改的一件事**：拖动过程中引擎那边这座建筑**还在原位**
  （还从原位开火、还在原位挨打），只有画面把它挪走了，松手才真的搬。
  这一版先把"看得见"修好；要不要让它在手上时停火 / 免疫，是玩法决定，
  不是渲染决定。
  → **同一天晚些时候这条有答案了，见下面「战斗期间不许动建筑」。**
  用户没选"拎起来停火 / 免疫"，选的是**根本不让它在打的时候被拎起来**。

  **2026-09-27（同一天，再晚一点）：战斗期间不许动建筑。**
  用户的原话是「在战斗的时候不能影响建筑不久可以了，你懂么」——
  回的就是上面那条悬着的问题。**不去定义"拎在半空算不算在场"，
  而是取消这个状态**：一波正在打的时候，放新的 / 挪 / 升级三件事一起锁。

  - **规矩只有一句问话**：`Battlefield.canReworkBuildings()` = `enemies.isEmpty()`。
    **判的是"场上有敌人"，不是"这一局没结束"**——两波之间的空当（以及开局）
    本来就该留给玩家摆位和升级，整局锁死的话这个游戏就只剩看。
    没按 `outcome() != ONGOING` 走，就是为了保住那个空当。
  - **拦在界面层，不在 `place` / `moveAll` / `upgrade` 里。** 那三个方法
    同时是**摆场景的 API**：`MainActivity.buildDemoScene` 和大量引擎测试
    都拿它们铺初始阵型，而铺的时候场上未必干净（测试里普遍是"先 `place`
    再 `spawn` 敌人来试射界"）。在那里面加一道"有敌人就拒绝"等于把摆场景和
    玩家操作混成一条路，一多半现成用例会当场变红——**先用脚本扫过 172 处
    变更调用，确认这个担心是真的**（`spawn` 和 `place` 在同一个方法里挨着的
    有五处，逐一读过才发现都是两条不同 `Battlefield` 实例上的，所以纯从
    调用序列看是分辨不出来的）。所以规矩由界面来问、界面来挡，
    和 `canPlace` / "买不买得起"同一层。
  - **五个入口各挡一次**，不是一个总开关：`beginDrag` 不进 `RELOCATE` / `BUILD`
    （落到 `PAN` 上，所以**拖视野照旧**）、`updateGhost` 一块虚影都不画、
    `tryPlace`、`buildLine`、`handleMoveTap` / `commitMoveDrag`；
    `MainActivity` 那边是商店的 `pick` 和升级框的 `upgradeInspected`。
    `BattlefieldView.reworkLocked()` 是视图这边唯一的判据，`MainActivity.inCombat()`
    转发同一句话——**两边各写一份判断迟早会有一边先改**。
  - **`updateGhost` 和 `carrying()` 那两问不是多余的**：`beginDrag` 只在
    ACTION_DOWN 那一下问。玩家按住一座塔不放、另一根手指去点"开始波次"，
    敌人就在这一拖进行到一半时进场了，而 `drag` 还是按下时定下的 `RELOCATE`。
    少了它们，画面上会继续跟着手指拖出落点虚影、塔也继续悬在半空——
    松手却什么都不发生。现在锁上的那一帧，手上那批**立刻回到地上**
    （`carrying()` 一处管住贴图 / 血条 / 射界 / 炮口火光 / 操作条五个消费者，
    在五个地方各判一次迟早漏一处，漏掉那处会留下一座浮在空中的塔）。
  - **锁上之后拖建筑 = 拖地图，而且不弹提示。** 这是刻意的：拖视野本来就
    允许，在建筑上按下和按在草地上按下分不出来，每拖一下弹一句
    "打起来了"比不弹还糟。**提示只给"看起来像改建筑"的那几个动作**
    （商店挑货 / 点升级 / 落子）——它们不成的原因是**同一个**（这一波没打完），
    所以共用一句 `bld_in_combat`，而不是复用 `shop_no_room`（那句言下之意是
    "换个地方"）或 `bld_need_more`（"去赚资源"）：换哪儿、赚多少都没用。
    也因此单开了 `Inspector.onReworkBlocked()`（默认空实现），没并进
    `BuildGate.onBlocked`。
  - **升级那一问排在问价前面**：这一下不成的原因是"现在不让动"，不是"钱不够"。
    反过来的话，钱包正好不够的玩家会收到"去赚资源"，等他赚回来这波早打完了。

  **这一版加了两条单测**（`BattlefieldTest`，**309 个测试 / 0 失败 / 1 跳过**）：
  「打起来了就锁、一波清完就解锁」和「一波都没发过但场上有敌人也锁」。
  第二条是钉住"判的是场上有没有人，不是发过几波"——不然这条规矩会变成
  "发过波次之后才生效"。视图层挡下来那一半没有单测（`BattlefieldView`
  整个不在 JVM 单测够得着的范围里，和上一版同一个理由）。

  **真机验证走的是像素，不是眼力。** 这台机器上一张截图 ~1s，
  而拖到一半的状态只在手指按住时存在，所以是
  `input motionevent DOWN/MOVE` 之后截图。判据三条：
  ①落点虚影那个绿边是**固定色 `(102,188,96)`**，整屏数它有多少个像素——
  清场后拖是 287 个，开打后拖是 **0** 个；
  ②相机确实动了（金色选中框从 x 406–517 移到 566–677，正是手指走的 160px），
  说明事件真送到了，不是"没测到"；
  ③拿**墙那一列**当不动的地标，量"墙右缘 → 塔左缘"的距离——
  拖动前 164px，拖动后 164px，**塔在格子坐标里一步没挪**。
  另外三条入口（升级 / 商店挑货 / 落子）各截到了
  "Cannot change buildings during a wave"，且等级没涨、货没拿到手上、地上没多出建筑。
  中间踩过一次坑：**头一轮"验过了"是假的**——`adb shell input tap` 打在了
  操作条的另一个框上（那条操作条会跟着相机平移，位置是我照着上一轮记的），
  而且当时 app 进程还是装 APK 之前那个，**跑的是旧代码**。这两件事都靠
  "先 force-stop 再 launch、每次点之前现 dump 一次 UI 拿真实 bounds"解决。
- **HUD 上的数字是"取整后相加"，不是"相加后取整"**：三个桶各自按显示精度
  取整，大数字用这三个整数加。真机上撞到过 4.73M + 3.25M + 871.0K 加起来是
  8.85M、大数字却写 8.84M——三个数并排摆着，读者一定会去加，差一整格就成了
  "这软件在骗我"。算术和理由在 `util/TokenFormat`，`TokenFormatTest` 盯着它。
  **换精度时要连着改 `MainActivity.showHud`**，那里不能再直接用 `bundle.total()`。
- **HUD 上是三个桶，和三种资源一一对应**：Input (uncached) / Cache (read + write) /
  Output，三个加起来正好等于上面那个大数字。
  **这是"显示"的合并，不是数据的合并**：`TokenBundle` 里仍然是四个字段、分开计价
  （读缓存 $0.30/1M 对写缓存 $3.75/1M，差十几倍，混在一起账单永远对不上）。
  合并只能发生在两个缓存桶之间——**不能把缓存并进 `input`**：那显示的是"输入总量"，
  而 `input` 这个字段本身只是其中没命中缓存的那一段，资源正是从这一段换来的
  （口径见 `CONTRACTS.md` §8）。所以那一格的文案是 `Input (uncached)` 而不是 `Input`，
  改文案之前先读 `strings.xml` 里那段注释。
  资源余额挪进了商店：它和价格放在一起才读得懂。操作行删掉的那行换算率小字也挪进去了。
- 资源来自结算：`SeasonRepository.settleCompletedDays(uid)` 发资源，
  三种资源互不通兑（`CONTRACTS.md` §8）。
  现在的价格：塔吃 CACHE + OUTPUT、墙吃 INPUT、核心免费——**三种资源都各有去处**，
  否则结算发下来的资源没地方花。`ShopCatalogTest` 盯着这条。
- 波次由玩家点开始，跑起来不能卡住界面（放后台线程或按帧推进）。

**开源**：大纲 §8 写了「an open-source tower-defence sample may supply the wave and
placement loop」——波次与放置循环**可以**基于现成的开源塔防样例改。

**现状：引擎一行都没用。** `game/engine/` 八个类全部手写，只 import `java.util`，
不含任何第三方塔防代码或素材，所以**报告的开源使用那一节不需要给引擎署名**
（要署名的是美术那批 AI 生成图，见 [`ART.md`](ART.md) §6）。

**但"引擎没用"不等于"整个项目没用"。** 数据侧已经引了两个开源库
（Room 2.8.5、MPAndroidChart v3.1.0，都是 Apache-2.0），报告的**开源那一节要写它们**
——清单、许可证出处、谁在用，全在 [`OPEN_SOURCE.md`](OPEN_SOURCE.md)。
别拿这一段的"零命中"去回答整份报告的开源问题。

以后真去借样例的话，用之前记下**项目名、仓库地址、许可证**，写进报告里那一节
（评分细则里占 15%）。许可证要能用于课程作业（Apache-2.0 / MIT 这类可以，
GPL 要谨慎）。判断"借没借"最简单的办法：`grep -rniE "copyright|licensed under|
SPDX" app/src/main/java`，现在应该是零命中——**这个 grep 只查得到"代码里拷没拷"，
查不出"gradle 里引了什么"**，依赖要另外看 [`OPEN_SOURCE.md`](OPEN_SOURCE.md) §1 那张表。

### 3.2 结算（`SeasonRepository`）

四个方法：`currentSeason`、`settleCompletedDays`、`spend`。
规则见 `CONTRACTS.md` §7 和 `SeasonState` 的类注释，五条都不能绕：

1. 今天永远不结算；2. 幂等；3. 补齐（三天没开一次补三天）；4. 已结算的天不可变；
5. `lastSettledDay` 和余额以服务端为准。

`settleCompletedDays` **故意不接受「结算哪一天」这个参数**——调用方说不了算。

### 3.3 agent（`agent/` + `AdviceRepository`）

- 服务端跑模型调用和函数调用循环，客户端**不持有任何模型 API key**（大纲 §8）。
- 五个工具全部只读，按 `AgentTool` 的白名单分发，名单外一律拒绝。
- 每个返回数字的工具都要带 `Coverage`，缺失的天**强制**写进 `AdviceAnswer.missingData`。
- agent 自己的 token 单独记账（`ownCostThisMonth`），不和被追踪的编码 agent 混在一起。
- 只比费用和 token，**不比输出质量**。

### 3.4 验收标准

- [ ] `settleCompletedDays` 连调两次，第二天余额不变（幂等），返回值第二次的
      `settledDays` 为空。
- [ ] 中间隔三天没打开，一次调用补齐三天，`settledDays` 有三项。
- [ ] 当天的用量**不会**被结算。
- [ ] 资源买塔之后余额真的减少，且余额减不成负数。
- [ ] 一波敌人能开始并打完，过程中界面不卡（能滚动、能点别的东西）。
- [ ] agent 问「为什么这周变贵了」，答案里有具体数字和缺失数据的说明；
      问一个没有数据支撑的问题时，它会承认不知道而不是编。
- [ ] `game/engine/` 下没有 `import android.`。
