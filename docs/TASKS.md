# 待办与验收标准

三个人各做一块。这份文档回答三个问题：**我该做什么、怎么算做完、卡住了找谁。**

> 给用 AI 读代码的人：契约字段的含义以 `app/src/main/java/com/mobilegroup20/tokentrail/contract/`
> 下的类注释为准，本文只讲「要做什么」。每个包还有一份 `package-info.java` 写该放什么。
> 接口的完整方法列表见 `docs/CONTRACTS.md`，或直接看 `data/repository/` 下的五个接口。

## 0. 所有人先看这四条

1. **只用接口，不用实现。** 拿对象走 `RepositoryProvider.usage()` 这样的调用，
   不要在界面里 `new` 别人的实现类。原因见 [`README.md` §2](README.md#2-依赖方向只有一个)。
2. **改 `contract/` 里的字段要先在群里说。** 那是三个人共用的，悄悄改会让别人的代码
   编译不过。改代码和改 `CONTRACTS.md` 放同一个提交里。
3. **每个新类上面写清楚：归谁、干什么、有什么坑。** 注释是写给队友（和他的 AI）看的，
   不是写给自己回忆的。
4. **金额一律用微美元（`long`）算，`double` 一次都不要出现。** 换成人民币只在最后
   显示的那一步做，而且只在数据侧做（见 `CONTRACTS.md` §9）。

## 1. 张莉 —— 数据侧

大纲里的分工：认证、用量日志导入、Room/服务端存储、版本化定价、预算、面板。
**这一块是整条链路的地基**，另外两个人的界面全部依赖它给出的数字。

### 1.1 要实现的接口

`data/repository/UsageRepository.java`（7 个方法）和
`data/repository/BudgetRepository.java`（3 个方法）。签名照抄，别改。

| 方法 | 干什么 | 关键点 |
| --- | --- | --- |
| `importCalls(uid, calls)` | 导入一批原始记录 | **按 `UsageCall.id` 去重**，靠 Room 唯一索引 + `OnConflictStrategy.IGNORE`，返回 -1 即重复。`ImportResult` 三个计数要如实填：新增 / 重复 / 拒绝 |
| `dailyUsageFor(uid, day)` | 某天的汇总 | 只返回 `Source.IMPORTED` 的记录 |
| `dailyUsageIn(uid, from, to)` | 区间的汇总 | 区间**两端都含** |
| `monthTokens(uid, month)` | 某月四类 token 合计 | 游戏侧结算读它 |
| `summary(uid, from, to, groupBy)` | 面板用的汇总 | `Coverage` 必须填对：有数据的天数和缺失的天数 |
| `compare(uid, from, to, metric)` | 三家对比 | 只比算得出来的量（token、费用、单位成本），**不比「哪个模型更聪明」** |
| `rateFor(provider, model, day)` | 查某天的费率 | 按 `effectiveFrom` 取「不晚于该天的最近一版」，见 `PricingRate` |
| `budgetOf` / `saveBudget` / `status` | 预算上限 | 只存上限，**花销从来现算**，不存「已花」 |

### 1.2 放哪

`data/local/`（Room 三张表，见 `CONTRACTS.md` §5）、`data/remote/`（自建服务端的读写）、
`data/importer/`（日志解析）。实现类写完后在 `RepositoryProvider` 里接上。

### 1.3 汇率

微美元 → 人民币的汇率、四舍五入由**你这边**定，写在数据侧；界面只显示结果，
不自己做乘法（`CONTRACTS.md` §9）。计价本身全程用微美元，汇率只影响显示。

### 1.4 验收标准

- [ ] 同一个日志文件导入两次，`inserted` 第二次是 0，`skippedDuplicates` 等于第一次的条数，
      总额不变。
- [ ] 一笔 3 美元/百万 token 的记录，300 万 token 算出来正好是 9 美元，
      不出现 8.999999。
- [ ] 改一版费率后重算，历史那几天的金额**不变**，`DailyUsage.rateVersion` 跟着变。
- [ ] 查询只返回本人的记录：登 A 账号看不到 B 的任何数字。
- [ ] `Coverage.daysMissing` 在缺数据的日子里真的会涨（不是永远 0）。
- [ ] 空区间、反向区间、只有一天，三种情况都不崩。

`ContractMathTest` 里已经有 12 个测试盯着这些口径，实现时对照着看。
**卡住了找谁**：费率区间和 `Coverage` 的口径找刘宗润（他写的 `contract/tool/`）。

## 2. 汪庭栋 —— 论坛

大纲里的分工：论坛的帖子数据与排序。

### 2.1 当前实现与新接口

论坛采用 **News / Community 两标签 + ＋发帖**。所有登录用户共享公共帖子池；“我的帖子”只是作者筛选，不是私密内容。支持最多 9 张图片、点赞、文字评论、分页与失败重试。

新版 UI 通过 `ForumFeedRepository` → `HttpForumRepository`；现有 `ForumRepository` 的 agent 接口保留。完整契约及账号接入步骤见 [`FORUM_API.md`](FORUM_API.md)。媒体新闻是独立 `NewsArticle`，不能混成官方帖子。

### 2.2 排序与数据

- 社区页面按发布时间与 ID 倒序；评论按时间与 ID 正序。
- agent 热帖排序继续由服务端计算 rankScore；现在已有点赞交互，可以纳入真实点赞数据，但不得由客户端自行重排。
- 用量、预算仍按 uid 私有；论坛帖子与评论跨账号公共可读。
- RSS 采集工具在 `tools/news/`，每小时由团队后端调度、导入新闻表。新闻英文为主，仅 App 内更新。

### 2.3 接入状态与验收

开发期已提供“免账号测试”：调试 APK 进入独立测试区，自动获得临时身份，可以独立于账号负责人测试真实新闻、图文、点赞和评论。测试数据不进入正式帖子池，Release 构建隐藏该入口。

Android UI、HTTP 适配、账号登录和 RSS 工具已实现；论坛后端已部署到现有服务器，复用 aibox_backend 的登录账号，公网 HTTPS 双账号联调通过。部署和维护见 [`backend/README.md`](../backend/README.md)。没有 API 配置时显示准备中，不用模拟数据冒充公共池。

## 3. 刘宗润 —— 游戏与 agent

大纲里的分工：塔防游戏、服务端建议服务、五个只读工具、建议效果评估。

### 3.1 塔防引擎（`game/engine/`）

**这个包不许 import 任何 `android.*`。** 玩法逻辑（网格、放塔、敌人路径、波次、
伤害结算）写成纯 Java，这样能脱离模拟器跑单元测试，也方便调平衡。

- **几何和相机已经写好了**：`BoardGeometry`（格子 ↔ 布局坐标换算、占地判定）、
  `Cell`（格子坐标，可直接当 Map 的 key）、`Viewport`（缩放 1–2 倍 + 拖动，
  焦点缩放，拖不出空白，开局贴最右边缘），共 48 个测试（BoardGeometry 25 + Viewport 23）；
  摆建筑、占位、地形分区、核心挪动、敌人推进在 `Battlefield`（65 个测试）；
  寻路那张表在 `PathField`（12 个测试），子弹在 `Projectile`（5 个）；
  数值和价格的配平在 `Cost`/`BuildingStats`（21 个）和 `ShopCatalog`（12 个）
  ——**"弩车的 DPS 必须压在箭塔下面""弩车比箭塔贵"这类话都写成了断言**，
  它们不是注释，改数就会炸。
  整个 `game/engine/` 现在是 **164** 个测试（含 1 个跳过的 `DemoSceneProbeTest`）；
  **全项目 223 个**（另有 `contract` 12、`util` 13、`data.local` 17、
  `data.remote` 9、`ui.forum` 7、根包 1）——这两个数别混，
  223 是整个工程的总数，不是这个包的。
  玩法逻辑<b>只用 `Cell`，不要碰屏幕像素</b>；触摸事件走
  `视口换算回布局坐标 → BoardGeometry 找格子` 这条路。
  格子尺寸、贴图规格、缩放规则见 [`ART.md`](ART.md) §2、§5。
- **相机里已经踩过的一个坑**：`Viewport.zoomAt` 反解新平移量时**不能减
  `offsetX()`**——`offsetX()` 里含 `panX`，而 `panX` 正是这一步要求的东西，
  减了等于把**上一个**平移量算两遍。表现是「放大 → 拖到边上 → 再捏」时
  画面先闪回中间才开始缩放。要用不含 pan 的 `centredOffsetX()`。
  这个错在「没拖过就捏」的情况下完全看不出来（旧 pan 是 0），
  所以**测焦点缩放的用例必须从"已经拖过"的状态开始**，
  `ViewportTest` 里那两条回归测试就是这么写的。
- **战场固定 40 列 × 18 行**（`BoardGeometry.COLS` / `ROWS`），所有设备一样。
  **格子大小只由屏幕高度算**（让 18 行 + 上方余量正好装下），所以
  **纵向一屏看得全 18 条路、横向一定要拖**（手机一屏约 16 列，40 格 = 2.6 屏）。
  这个取舍的理由写在 `BoardGeometry.COLS` 的注释里：漏看一路等于漏掉整局，
  横向看不全只是多拖两步。
- **贴图接上了一半：两种塔（各三级）是真图，核心和城墙还是色块**（2026-09-26/27）。
  `game/view/BuildingSprites` 按「种类 + 等级」取图，`BattlefieldView.drawBuilding`
  有图就画图、没图就退回 `drawBlock(...)` 的色块——**两种画法同时存在是故意的**，
  美术是一张张补上来的，中间态要能跑。图的宽高比在构造函数里按设计尺寸校一遍，
  对不上当场抛；色块那边的尺寸和锚点本来就按真贴图规格画的，所以换图不动布局。
  真机实测（华为 HBN-AL80）：一格 23.9dp，一屏 15.6 列，开局镜头贴最右边缘。
  界面占掉 45% 屏高是格子这么小的主要原因，见 [`ART.md`](ART.md) §5。
- **塔贴图是镜像过的，而且这批图量出了塔的占地**（2026-09-27）。
  六张原图炮口**全朝右**，游戏里塔一律朝左打，所以在抠图脚本里统一翻了一次
  （`art/cut_tower.py`，四步：抠底 → 水平镜像 → 裁内容边界 → 缩到成品尺寸并贴底）。
  **画布边界是量出来的**：把"底座踩地那一行"定成正好 2 格（= 占地宽），
  炮管就落在左边 1.03 格、炮尾落在右边 0.28 格，取整成 1.0 / 0.3，
  于是画布 3.3 × 2 格 = 845 × 512（`BuildingType.TOWER` 的三个 overhang 字段）。
  取整误差不到 0.03 格（屏上约 2px）；脚本每次跑完会用踩地那一段反过来验一遍。
- **开火的时候炮口有一团火**（2026-09-27）。`BuildingSprites` 里除塔本身还管
  三张**炮口火焰**（589×512），`BattlefieldView.drawMuzzleFlashes` 在
  `FLASH_SECONDS`（0.12 秒）内把它盖在塔贴图上、线性淡出。
  - **为什么是"叠一层"不是"换一张整塔图"**：开火那三张原图是重画过的，
    塔身在两张图里差了约 1.25 倍（一级素图底座踩地 879px、开火图 697px），
    整张换上去塔身会跳一下。只抠火焰那块叠上去，塔身始终是原来那张。
    做法（按颜色挑暖色那一团、按"踩地 = 2 格"定比例、按炮尾对齐）写在
    `art/cut_muzzle_flash.py` 开头，[`ART.md`](ART.md) §2.1 有摘要。
  - **"刚开了一炮"没有新增引擎字段**：装填计时是"开火时加满、之后每帧减"，
    所以 `射速间隔 - 剩余装填` 就是离上一发过去多久，直接在视图里算。
    塔空闲时引擎会把装填夹回 0，这个差正好等于一整个间隔，天然不画。
  - **没做的**：`docs/ART.md` §4 里那三种"爆炸 / 命中火花"还空着。
- **第二种塔：弩车**（2026-09-27）。**引擎那边一行没改**——`BuildingStats.hasRange`
  多一个或号、`isTarget`/`stepCost` 本来就只对墙例外，所以"多一种塔"在玩法侧
  就是**多一张数值表 + 多一行货架**。改的是这四处：
  - `BuildingType.BALLISTA`：2×2，弩弓朝左探 0.9 格、弩尾 0.2 格（**和箭塔的
    1.0 / 0.3 不一样**）。占地相同、贴图不同宽，这正是"占地和探出分开"的意义。
  - `BuildingStats` 里一张新表：射程 3.0/3.5/4.0、单发 34/45/58、
    间隔 2.6/2.4/2.2、血 80/105/130。**和箭塔是反着配的**（慢而重 对 快而轻），
    硬约束是 **DPS 必须更低**（13.1/18.8/26.4 对 14/20/28）——射程远、单发重、
    DPS 还高的话，箭塔就没有存在理由了。这条有测试盯着（`CostTest`）。
  - `ShopCatalog`：CACHE 45 + OUTPUT 18（箭塔 25 + 10，差不多两倍）。
    升级价跟着建造价走，也吃同样两种资源。
  - `MainActivity.buildDemoScene`：**第 32 列**摆了三级各一座（**显示架**，
    一级/二级/三级并排，一眼看出三级的美术差别）；`upgradeToLevel` 是那个帮手。
    **箭塔那边还差一档**：演示场面里五座一级、一座二级（第 14 列那座），
    **三级箭塔的贴图在场上还没有一座**——要看的话得自己在游戏里升，
    或者照弩车那样也摆一条。
- **弩车一开始摆在错的那一侧**（2026-09-27 当天发现并改掉）。
  第一版把三座弩车摆在**第 26 列**，也就是第二道城墙和箭塔群**之间**——
  站在敌人往核心去的必经之路上。结果上了真机才发现：**弩车薄（80/105/130）、
  射界又只朝左 60°，摆在最前面就是替箭塔挨打**，一座弩车活不过 20 秒，
  屏幕上根本看不到它开火。这才回头去读 `BuildingStats` 里自己写的那句
  "弩车射程远，本来就该摆在箭塔后面"——摆位和设计意图是反的。
  - **换到第 32 列（箭塔后面、紧挨核心）之后，同一套场面在无头探针里**：
    弩车三座合计开火 **12 发 → 54 发**，一级那座从"活 53 秒"变成"活 280 秒"，
    二级和三级**活到最后**；六座箭塔的合计开火数也从 25 涨到 53
    （弩车把漏过去的敌人补掉了）。20 个种子的探针仍然 **0/20 守住**，
    但崩在第 5 波的从 0 个变成 8 个，最长一局从 ~200 秒拉到 325 秒。
  - **教训写在这儿**：射界只有 60° 且固定在左边之后，"摆在哪一列"不再是
    美术问题而是玩法问题——**摆在敌人来的那一侧**（左边）会先挨打，
    **摆在敌人要去的目标那一侧**（右边）才既打得到又活得久。
    加第三种塔的时候先拿这个探针量一遍，别照着"看着顺眼"摆。
- **弩车开火是"整张叠一层"，和箭塔的炮口火焰不是一回事**（2026-09-27）。
  箭塔那批原图的素图和开火图是**重画过的**（塔身差了 1.25 倍），所以只能抠炮口那一小块；
  弩车这批**是同一张渲染加一层发光**——两版"踩地那一段"像素级一致
  （819/819、821/821），把底边对齐后弩身重合度 0.968 / 0.936。所以直接抠出整层发光，
  窗口就是整张贴图（`BuildingSprites.FLASH_WINDOWS` 里弩车是 `(0, 3.1)`，
  箭塔是 `(-1.5, 0.8)`）。判据是**亮度增量**不是颜色差（弩身本来就满是青符文，
  按颜色差会把整条弩身染蓝）。**二级那张的放电画在尾部**，单独翻了一下——
  `art/cut_ballista.py` 里的 `GLOW_FLIP = {2}`，别把另外两级加进去。
  **这条判据给了以后一个选择题**：先问"两个状态是不是同一张图"，是就整张叠，
  不是才去抠那一小块（[`ART.md`](ART.md) §2.1 有这段的完整版）。
- **敌人也换上真贴图了：三张方图，三种兵共用**（2026-09-27）。
  原图交付的是**同一个人的三个动作**——迈步走（脚下带扬起的土）、抡键盘砸
  （甩出一道青电弧）、站着不动，正好对上引擎已有的三个状态，所以
  `game/view/EnemySprites` 就三张 422×422 的图，一种兵一张都不用多。
  - **"三种兵长得一样"不是偷懒，是原图就是这样**。三张贴图分不出杂兵 / 快兵 /
    重甲，所以区分改由两件事承担：**体格**（`EnemyType.bodyCells`，三种差 1.56 倍，
    直接乘在贴图矩形上）和**脚下那圈颜色**（深色接地影 + 一圈种类色的边）。
    `colors.xml` 里那三个敌人色**没删**，是从"填满身体"改成"垫在脚底"了——
    给一张几百种颜色的像素画整体染色会糊成一团，垫在脚下既保住画，又顺手当了接地影。
    真机验过三种色都认得出（红 2722px / 黄 1071px / 紫 174px）。
  - **画布是正方形、边长只有一个合法值**（422px = 体格 1.25 × 1.32 格 × 256）。
    这是拿"整体被缩放了一档"这类错误没办法的办法：等比缩放不改变宽高比，
    `BuildingSprites` 那种校比例的做法查不出来，方画布把边长卡死就查得出来。
  - **走路按"走过几格"翻帧，不按时间**：走 0.7 格换一帧，所以快兵步频快、
    慢兵步频慢，脚不打滑；按时间翻的话三种兵会同一个步频平移，快兵看着像在滑板。
    啃建筑的挥击则相反，**按本机时钟**（0.62 秒一轮，前 62% 抡下去、后 38% 收势），
    因为"啃了多久"是观感不是玩法。
  - **"走过几格"这个数是引擎记的（`Enemy.travelled`），不是 `enemy.x`。**
    第一版图省事直接拿了 `enemy.x`，看着够用——x 一直在涨，走路也确实主要往右走。
    上了真机才看出来：**敌人拐弯是竖着走的**，那几格 `x` 一动不动，于是整只敌人
    平移着上去、腿一下都不迈。所以加了一个只增不减的**路程**字段，
    记在 `Battlefield.stepToward` 里——那是全项目唯一一处改敌人坐标的地方，
    横着走、竖着走、斜着拐弯都在那儿，记一份就全对了。
    拿 `x + y` 之类凑一个数不行：拐弯那一段是斜着过去的（朝的是下一格的中心），
    两个坐标同时涨，凑出来的数涨得比真路程快。
    演示场面的实测（60fps，三个种子）：**纯纵向的帧一共 1848 帧，
    按 `x` 翻帧 0 次、按 `travelled` 翻帧 38 次**——差的就是这一段。
  - **挥击是本机时钟、走路是引擎字段，两个动画都不新增计时器**：
    引擎本来就只给得出"卡住了"（`Enemy.blocked`），给不出"啃到第几口"，
    所以挥击只能挂在时钟上；走路挂在路程上，一分钱时钟都不用花。
    这一版引擎只多了 `travelled` 一个字段（+3 个测试），玩法逻辑一行没改。
  - **没有做**：敌人之间仍然不互相挡（汇到缺口会叠成一坨），
    这是从第一天就定下的取舍，没变。
- **战斗已经做完并真机验过**：`Battlefield.advance` 一帧四步——塔开火、子弹飞、
  敌人移动、清场。敌人被挡住就啃挡它的那一座，啃穿的建筑当帧就从场上和占位表里消失。
  三种敌人（杂兵 / 快兵 / 重甲）数值在 `EnemyType`，颜色和体格在 `colors.xml`
  和 `EnemyType.bodyCells`——**体格同时是判定用的身位**（射程判"圈碰到身子"、
  挡路判"身体边缘碰到"），画的和判的是同一个数。
- **塔打的是子弹，不再是持续照射**（`game/engine/Projectile.java`，2026-09-25 加）。
  伤害从"每秒扣多少点"变成"每发多少 + 几秒一发"：
  `BuildingStats.damagePerShot`（14/18/21）× `fireIntervalSeconds`（1.0/0.9/0.75），
  **两个数除一下正好是原来那三个每秒伤害**（14/20/28），所以平衡没动，
  动的是观感：出膛和掉血之间多了一个看得见的过程。
  子弹飞 9 格/秒，最远射程（3.5 格）0.39 秒到；真机上连拍 12 帧有 3 帧能扫到子弹
  （0.25 秒 ÷ 1 秒，和算出来的占空比一样），直径 26.6px = `SHOT_CELLS` 0.3 格。
  **子弹是追着目标打的**，不是朝一个方向飞出去：敌人现在会拐弯（`PathField`），
  固定方向的子弹会在它换行那几帧擦身而过，而"差一点没打中"玩家既控制不了、
  也没法手算。追着打的前提是<b>子弹比最快的敌人快得多</b>（9 对快兵 1.6），
  这条硬要求写在 `PROJECTILE_SPEED_CELLS_PER_SEC` 里，`ProjectileTest` 盯着它。
  目标半路死了，子弹把剩下的路飞完再消失（不凭空不见），但不扣血——
  这也正是以后加溅射的位置：那时结算的就是"落点周围有谁"。
- **"天上已经有几发"要算进挑目标里**（`Battlefield.damageInFlightAt`）。
  少了这一问，六座塔会在同一帧对着同一只 28 血的快兵各吐一发：前两发打死、
  后四发全打空。有了它，塔挑目标时会先看"这一只是不是已经被安排掉了"，
  火力自己铺开——**一座塔看不出区别，五座塔一起打一波时全靠这一条**。
  顺带一个反直觉的结论：**"打空"其实造不出来**。每座塔开火前都要求
  "剩余血量 > 天上已有的伤害"，所以一只敌人一定是被最后落地的那一发打死的，
  天上不会有跟着白飞的子弹。`BattlefieldTest` 里那条"子弹落地时目标已经不在"
  是纯防守性的（测试里得直接把血按到 0 才造得出那个局面）。
- **塔打"最靠前"的那只，敌人去"最近的建筑"、咬"挨着最近"的那座**（2026-09-25 定）。
  这两条是<b>分开</b>定的，别当成一对对称的规则：
  - 塔：挑射程内**寻路表上离核心最近**的那只（`frontmostInRange`）。
    "最靠前"按表算，**不按 x**——敌人会绕路，一只拐到上面去的可能 x 更小
    而其实更接近核心。"打离自己最近的那只"试过一版，又改回来了，理由是
    **实测**：20 个种子的演示场面里"最靠前"守住 6 个、"就近"只守住 3 个
    （那时敌人还是"一路奔核心"，见下面配平那节的表）。差距不大，但方向是稳的。
    代价是纵向错开时塔会越过贴脸的那只去打斜对面的，看着像装看不见——
    但塔防里"该拦的那只多走几步"就是漏怪，这个代价比画面别扭大。
    （`aTowerShootsTheEnemyFurthestAlongNotTheNearestOne`，两只敌人特意摆成
    "一只在靠近、一只已经走过去"，两种规则才分得开。）
  - 敌人：**去的方向和咬谁都是"最近的建筑"**，塔和核心**优先级相同**
    （2026-09-25 改）。寻路表的目标集合是**所有塔 + 核心**（`Battlefield.isTarget`），
    墙不在里面——所以一座塔只要比核心近，敌人就是冲着塔来的，会绕路过去拆。
    **核心不再是天然终点**，"把敌人放进来让它们打塔"这件事以前根本不存在。
    停下来之后咬谁见下一条 `nearestBite`。
    - 这一条是用户提的那个问题的落点："敌人明明贴着塔，为什么还是奔核心去"。
      根因是**结构上的不对称**：从前目标是核心一个，塔只是"很贵的地"。
      修法不是调数值，是把塔也放进目标集合。
    - 表里因此有**两张**：`path`（所有塔 + 核心，管去哪儿）和 `corePath`
      （只有核心，管"谁最靠前"）。分两张是因为问的不是一件事——
      用 `path` 算进度的话，站在塔跟前啃塔的那些数值特别小、看着最"靠前"，
      塔就会集体去招呼它们，真正逼近核心的那只反而没人管。
    - **玩法后果：墙挡不住一个"目标是塔"的敌人，只能拖住它。**
      一座塔背后砌一格墙是没用的——敌人从旁边绕过去照样啃塔（
      `aTowerRightBehindAWallStillShootsWhatIsChewingIt` 的注释里记了这件事，
      那条测试因此得把墙砌成一整列才逼得出"啃墙"这个局面）。
      要把塔保住就得把通往它的路整个封上。
  - `progressOf` 的两个分支**方向必须一致**（有核心走 `corePath`，没核心退回
    "离右边界多远"）。写反了只在**场上没核心**时发作，正常对局永远走不到那一支，
    所以两条测试一条带核心、一条不带，合起来才盖全。
- **墙是唯一的例外。** 塔从来不把墙当目标（它本来就只打敌人）；
  敌人**只在寻路表真的指进墙里时才拆墙**，顺手够得着的墙不咬。
  少了后半条，重甲（身位 1.25，比杂兵宽）会放着挡在面前的塔不啃、
  转身去啃旁边那面没挡路的墙。所以**敌人那边的**候选里，墙只有站在 `blocker` 那一格
  （= 寻路表指着它 = 绕不过去）时才算数（`anEnemyBitesTheNearestBuildingButNeverAWallThatIsNotInItsWay`）。
- **绕墙、拆塔**（2026-09-25 改定，现在是"墙贵、塔和核心都是目的地"）。
  同一个位置换一种建筑，敌人的反应要分开：
  - **墙**：`BuildingStats.WALL_PATH_COST = 4096`（比整块战场 720 格加起来还大）
    → 任何绕路都比穿墙便宜 → **绕**。只有真的封死、绕不过去，表上的箭头才会
    指进墙里，敌人才动手拆（`Battlefield.stepCost` 是唯一的价钱表）。
  - **塔和核心**：**不参与价钱计算**，它们是寻路表的**目标**，那几格恒为 0
    → 箭头本来就指着它们 → 走过去，发现占着，**拆**。
  - 所以"拆塔"不再需要一个"塔很便宜"的数。**上一版那个按类型分的价钱表
    （`BuildingStats.pathCost`）已经删了**：塔进了目标集合之后，给塔的那一档
    （先后试过 20 和 1）是死代码——没有任何一处读得到它。留下 `WALL_PATH_COST`
    一个公开常量，`PathFieldTest.uniform()` 也用它。
  - **那个"塔价 20"是我算错了给出来的**（凭感觉说"有点贵"，量出来才发现分界是 3）。
    量法记在这儿：塔占 2×2 压住一条道时，绕过去多走 4 步，穿过去多花 `2 × 塔价`，
    所以"拆"的条件是 `塔价 < 3`——实测 2 拆、3 绕。**但那个分界跟着地形走**
    （塔贴着墙或夹在一格宽的走廊里，绕路可能只要 +2，分界就掉到 2 以下），
    于是同一个"塔价 2"，有的地方拆、有的地方绕，玩家看到的是"这两座明明一样摆，
    敌人只拆左边那座"。取 1 才没有这个问题。**这一段留着是因为它解释了为什么
    现在干脆不走价钱这条路**。
  - 代价是**摆在敌人道上的塔会被啃**——以前塔是绝对安全的。
    这是这条改动真正的玩法后果，演示场面那四座塔正好压在道上，见下面配平那节。
- **装填计时是"减 dt、开火时再加回去"**，不是"开火时赋值成间隔"。赋值会每发白丢
  一帧的时间（0.05 ÷ 1.0 = 5%），结果就是**帧率决定难易**：同一条路配同样的塔，
  60Hz 的手机守得住、120Hz 的守不住，而这种事在真机上基本查不出来。
  空闲时还要把负数夹回 0（不然一只敌人在圈外等了三秒，塔一进圈就补发三发，
  看着像卡了一下）。`BattlefieldTest.theFireRateDoesNotDependOnTheFrameRate`
  用两种帧长跑同一段时间，比挨的伤害。
- **画面上那层"塔→目标"的连线没了，改成画子弹本身**（`BattlefieldView.drawProjectiles`）。
  连线说不了"打出去的东西还没到"，于是敌人掉血看着像凭空发生；子弹能。
  **换真贴图只动 `drawProjectiles` 一处**：把那个 `drawCircle` 换成 `drawBitmap`、
  圆心对准 `(x, y)` 就行，尺寸见 `SHOT_CELLS`（规格已写进 [`ART.md`](ART.md) §4），
  引擎一个字都不用改——它只知道"有一颗子弹在这个坐标上"。
  **帧闸门也跟着改了**（`BattlefieldView.tick`）：判断"还要不要下一帧"从前只看
  "场上还有没有敌人"，现在还要看"天上还有没有子弹"。不改的话最后一波清空的那一刻
  画面就停了，**还在飞的那几发会僵在半路**（而且以后一直挂在那儿）。
- **敌人会自己找路去最近的建筑**（`game/engine/PathField.java`，2026-09-25 加）。
  从目标集合往外铺一张 Dijkstra 的"还有多远"表，敌人每帧只问一句"四邻里哪格更近"，
  所以**墙不是墙、是"很贵的地"**（空地 1、墙 4096、塔和核心是目标）：有缺口就绕缺口，
  围死了才动手拆。绕和拆因此不是两套规则，是同一张表在两种地形下的两个结果。
  表只在**建筑变了**的时候重铺（`place` / `remove` / `move` / `clear` → `pathDirty`），
  不是每帧。
  **这条改动修掉了一个"这一局根本输不了"的 bug**：从前敌人只直着走，而核心只占
  3 行（第 7–9 行），18 条路里只有那 3 条的敌人会撞上核心，其余 15 条的敌人一路走出
  右边缘——只记一笔漏怪，**核心一滴血都不掉**。五波打完永远算守住。
  现在敌人会拐弯，任何一行的敌人都摸得到核心，[`Outcome.OVERRUN`] 才是真的输。
  代价是敌人**全部汇到缺口和核心跟前**，于是下面那条"互相不挡"变得显眼得多。

  ⑧ 挪不过去时**留在挪动模式**，不要退回普通模式：想挪到墙边，手指点歪半格
  是常事，点歪一次就得回详情面板重新点一遍 Move 的话这个功能没法用。
  同理，正在挪的那一座**要一直亮着金边和范围圈**（`drawRanges` / `drawOverlay`），
  只在手指按着的时候画虚影是不够的——手指一抬屏幕上就没有任何东西说明
  "挪的是哪一座、它原来在哪儿"，玩家得自己记。

  **范围圈和真实判定现在是同一个数**（2026-09-25 战斗做完之后）：
  `BuildingStats.rangeCells` 既是画圈的半径，也是 `frontmostInRange` 的射程。
  判定额外加敌人的半个身位（`EnemyType.halfBodyCells()`——体格是逐只的，
  重甲比杂兵宽，所以它从更远处就开始挨打）——因为圈是"离我 N 格以内"，
  而敌人的判定点是中心，不加的话半个身子在圈里的反而不挨打。
  墙后紧贴的那座塔（差 0.05 格）就是这么救回来的，`BattlefieldTest` 里钉着这一条。
- **三种建筑都能升级**（2026-09-25 改的）。从前只有塔能升，墙和核心的
  `BuildingStats.upgradeCost` 直接返回 `null`；现在墙和核心也按级涨耐久
  （墙 150/220/320、核心 600/900/1300），于是那张表里
  **`null` 只剩一个意思：到顶了**，界面上也就不用再解释"这种建筑这个版本还不能升"
  ——那句文案和那个分支一起删了，留着就是一句永远显示不出来的话。
  升级吃哪种资源和建造价保持一致（塔 CACHE + OUTPUT、墙只吃 INPUT），
  因为三种资源不通兑，"造得起、升不起"是说不清的局面，`CostTest` 盯着这条对应关系。
  核心升级**故意和塔抢同一种资源**，还比塔贵：加厚核心是"承认自己会漏"，
  再摆一座塔是"争取不漏"，这个取舍是真的，所以核心升级不该是不要 OUTPUT 的便宜事。
  界面上"到顶了"那一条不变（按钮换成点不动的 Max level）。
- **详情面板上多了一行耐久**（`bld_hp`，2026-09-25 加的）。塔、墙、核心都有血，
  所以这一行不像攻击范围那样会整行 GONE。以前模型里三种建筑明明都有耐久，
  界面上却一处都不显示——"墙是有血的"这件事玩家根本看不出来，
  被打之前它看起来和装饰没区别。胶囊的圆点用血条那个绿（`game_hp_good`），
  和战场上那条血条同色：面板上的数字和地上那条杠说的是同一件事。
- **详情里有个 Move**（2026-09-25 加的）。和部落冲突一样：摆错了随时能改，
  **不花钱**，也不经过商店。这一条是"摆位是这游戏唯一的策略动作"的地基——
  只能一次性摆对的话，没人敢在开局就下手。

  挪动模式里点一下只有三种结果：**挪过去**（退出模式，顺手把详情弹回来——
  下一个动作十有八九是接着看它）、**挪不过去**（红闪 + 一句话，留在模式里，坑 ⑧）、
  **点到某座建筑**（取消挪动，改成查看那一座；点到它自己就是"算了，放这儿"）。

  | 谁 | 干什么 |
  | --- | --- |
  | `Battlefield.move` + `Building.relocateTo` | 挪任意一座建筑。**不花钱**，所以这条路不经过 `BuildGate`；**改坐标不是拆了重放**，`level` 带得走（坑 ⑤） |
  | `BattlefieldView.startMoving` / `handleMoveTap` | 挪动模式和它在触摸里的分支。和 `selected`（手上拎着要放新的）**互斥**：拎着一件要放新的、同时又在挪场上的一座，两个模式叠在一起，点一下空地该干什么是说不清的 |
  | `BattlefieldView.ghostType` / `ghostLevel` | 虚影是谁、按几级算。**虚影有两个来路**（要放新的 / 要挪旧的），画虚影的三处都靠这两个方法，别各写一遍三目 |
  | `res/layout/sheet_building.xml` 的 `bld_move` | 详情里的 Move 按钮。它在"次要操作"那一行，和 Close 并排、同一个样式——两件事都不改这一座的数值 |

  **挪动那条路和 `BuildGate` 无关**：那个关卡问的是"这件买得起吗"，而挪动不产生
  任何开销，所以 `updateMoveGhost` 里没有 `affordable` 这一问，界面也别给它加
  变暗逻辑（加了玩家会以为挪不起）。同理，挪不过去的提示是
  `bld_move_blocked`（只说位置），不是 `shop_need_more`（说钱）——
  借错那句话会把玩家引到钱包上去，而问题其实在位置。

  **已知冗余**：商店里选 Core 那条路（`BattlefieldView.movingCore`）现在和新功能
  重复了——"选中核心这一类点哪儿挪哪儿"和"指定这一座点哪儿挪哪儿"是同一件事。
  留着是因为商店里那行文案（`shop_size_core`："move the one you have"）已经把
  那条路讲给玩家了，删掉会让那句话落空。要收的话两处得一起收。
- **HUD 上的数字是"取整后相加"，不是"相加后取整"**：三个桶各自按显示精度
  取整，大数字用这三个整数加。真机上撞到过 4.73M + 3.25M + 871.0K 加起来是
  8.85M、大数字却写 8.84M——三个数并排摆着，读者一定会去加，差一整格就成了
  "这软件在骗我"。算术和理由在 `util/TokenFormat`，`TokenFormatTest` 盯着它。
  **换精度时要连着改 `MainActivity.showHud`**，那里不能再直接用 `bundle.total()`。
- **HUD 上是三个桶，和三种资源一一对应**：Input (uncached) / Cache (read + write) /
  Output，三个加起来正好等于上面那个大数字。
  **这是"显示"的合并，不是数据的合并**：`TokenBundle` 里仍然是四个字段、分开计价
  （读缓存 $0.30/1M 对写缓存 $3.75/1M，差十几倍，混在一起账单永远对不上）。
  合并只能发生在两个缓存桶之间——**不能把缓存并进 `input`**：那显示的是"输入总量"，
  而 `input` 这个字段本身只是其中没命中缓存的那一段，资源正是从这一段换来的
  （口径见 `CONTRACTS.md` §8）。所以那一格的文案是 `Input (uncached)` 而不是 `Input`，
  改文案之前先读 `strings.xml` 里那段注释。
  资源余额挪进了商店：它和价格放在一起才读得懂。操作行删掉的那行换算率小字也挪进去了。
- 资源来自结算：`SeasonRepository.settleCompletedDays(uid)` 发资源，
  三种资源互不通兑（`CONTRACTS.md` §8）。
  现在的价格：塔吃 CACHE + OUTPUT、墙吃 INPUT、核心免费——**三种资源都各有去处**，
  否则结算发下来的资源没地方花。`ShopCatalogTest` 盯着这条。
- 波次由玩家点开始，跑起来不能卡住界面（放后台线程或按帧推进）。

**开源**：大纲 §8 写了「an open-source tower-defence sample may supply the wave and
placement loop」——波次与放置循环**可以**基于现成的开源塔防样例改。

**现状：引擎一行都没用。** `game/engine/` 八个类全部手写，只 import `java.util`，
不含任何第三方塔防代码或素材，所以**报告的开源使用那一节不需要给引擎署名**
（要署名的是美术那批 AI 生成图，见 [`ART.md`](ART.md) §6）。

**但"引擎没用"不等于"整个项目没用"。** 数据侧已经引了两个开源库
（Room 2.8.5、MPAndroidChart v3.1.0，都是 Apache-2.0），报告的**开源那一节要写它们**
——清单、许可证出处、谁在用，全在 [`OPEN_SOURCE.md`](OPEN_SOURCE.md)。
别拿这一段的"零命中"去回答整份报告的开源问题。

以后真去借样例的话，用之前记下**项目名、仓库地址、许可证**，写进报告里那一节
（评分细则里占 15%）。许可证要能用于课程作业（Apache-2.0 / MIT 这类可以，
GPL 要谨慎）。判断"借没借"最简单的办法：`grep -rniE "copyright|licensed under|
SPDX" app/src/main/java`，现在应该是零命中——**这个 grep 只查得到"代码里拷没拷"，
查不出"gradle 里引了什么"**，依赖要另外看 [`OPEN_SOURCE.md`](OPEN_SOURCE.md) §1 那张表。

### 3.2 结算（`SeasonRepository`）

四个方法：`currentSeason`、`settleCompletedDays`、`spend`。
规则见 `CONTRACTS.md` §7 和 `SeasonState` 的类注释，五条都不能绕：

1. 今天永远不结算；2. 幂等；3. 补齐（三天没开一次补三天）；4. 已结算的天不可变；
5. `lastSettledDay` 和余额以服务端为准。

`settleCompletedDays` **故意不接受「结算哪一天」这个参数**——调用方说不了算。

### 3.3 agent（`agent/` + `AdviceRepository`）

- 服务端跑模型调用和函数调用循环，客户端**不持有任何模型 API key**（大纲 §8）。
- 五个工具全部只读，按 `AgentTool` 的白名单分发，名单外一律拒绝。
- 每个返回数字的工具都要带 `Coverage`，缺失的天**强制**写进 `AdviceAnswer.missingData`。
- agent 自己的 token 单独记账（`ownCostThisMonth`），不和被追踪的编码 agent 混在一起。
- 只比费用和 token，**不比输出质量**。

### 3.4 验收标准

- [ ] `settleCompletedDays` 连调两次，第二天余额不变（幂等），返回值第二次的
      `settledDays` 为空。
- [ ] 中间隔三天没打开，一次调用补齐三天，`settledDays` 有三项。
- [ ] 当天的用量**不会**被结算。
- [ ] 资源买塔之后余额真的减少，且余额减不成负数。
- [ ] 一波敌人能开始并打完，过程中界面不卡（能滚动、能点别的东西）。
- [ ] agent 问「为什么这周变贵了」，答案里有具体数字和缺失数据的说明；
      问一个没有数据支撑的问题时，它会承认不知道而不是编。
- [ ] `game/engine/` 下没有 `import android.`。
